## 2. 实测数据

### 2.1 缓存：**47 秒 → 0 秒**

同一篇 39,705 字论文、同一配置跑两次：

| | 第 1 次 | 第 2 次 |
|---|---|---|
| 日志 | `🧩 分块抽取 → ⚡ 4 路并发提交 → ⚡ 并发完成：18/18 块成功` | `♻️ 命中缓存（97756eaabab50c6af205077c），跳过调用` |
| 耗时 | **47 秒** | **0 秒** |
| 输出 | 1,455 字符 | 1,455 字符（与第 1 次一致） |

改提示词、改 LoRA、改 `temperature`/`chunk_size` 等任一项 → 缓存键变化 → 自动重新抽取，不会误用旧结果。

### 2.2 分块并发：**约 63 秒 → 47 秒**

18 块 / 4 并发。加速比不高（1.34×）的原因：vLLM 在 16GB 显存上批处理能力有限，
且总耗时由**最慢的那一块**决定（首块包含摘要+引言，输出最长）。

**结论**：并发有价值但不是数量级改善。若要进一步提速，应配合 `max_tokens` 自适应（路线图 B4）。

## 4. A4（无依赖节点并发）为什么推迟

不是"没时间"，是**当前形态下做了不安全**，具体三个障碍：

1. **共享状态竞态**：`LoraRouter.ensure()` 用共享的 `currently_loaded` 集合做 check-then-load，
   并发调用会让两个节点各自认为需要加载 LoRA，甚至互相换入换出。
2. **LoRA 常驻冲突**：`analyze_method` 用 `paper_analyzer_v6`、`extract_*` 用 `extract_v2`，
   `max_loras=2` 同时容纳；但若并行节点用不同 LoRA，调度顺序不可控，可能出现反复加载。
3. **控制流**：`fail_fast` 依赖循环内的 `break`，且节点日志是直接写 stdout 的（并行会交错），
   需要把节点体抽成函数 + 线程本地日志前缀 + 锁，改动约 200 行核心循环。

**成本/收益**：收益约占总时长 17%（B1 之后的主要耗时已是本地抽取，那部分不可并行成多节点）；
风险是**动核心循环**。按"已验证才发布"的既定原则，这一项需要单独的验证轮次。

**建议方案**（下一轮）：把节点体抽成 `execute_node(node, nid) -> effects`，
effects 收集后再顺序应用；`router.ensure` 加锁；并行波次仅在「同 LoRA 或均无 LoRA」时启用；
日志走线程本地前缀。

## 6. 怎么用

**日常调提示词（最大受益场景）**：`extract_method` 已开缓存 —— 同一篇论文反复跑，
本地抽取只做第一次（约 47 秒），之后每次 **0 秒**。

**手动清缓存**：删除 `cache/nodes/` 即可（或按需删单个 `*.json`）。
**临时关闭缓存**：环境变量 `WORKFLOW_CACHE=0`（作用于整个进程）。

**多配置**：在工作流页顶部的下拉里切换；"保存节点配置"与"运行分析"都作用于所选配置。
新增一套配置只需在项目根目录放一个 `workflow_config_<名字>.json`，下拉里会自动出现。
