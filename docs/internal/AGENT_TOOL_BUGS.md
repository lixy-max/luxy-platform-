# Agent 工具巡检结果（Node 版真调用）

**方法**：用 Node 直接调用 `window.AGENT_TOOLS.<name>.handler(args)`（`tests/frontend/e2e_tools.js`），
走**真实 fetch** 打真实后端 `:8001`，每个只读工具跑 **3 轮**；危险工具**只做参数校验检查**、不执行。

**环境**：44 个工具（只读 36 / 危险 8）、后端 690 测试通过。

## 汇总

| 判定 | 数量 | 说明 |
|---|---|---|
| always-ok | **19** | 无参或极简参数即可正常工作 |
| always-fail | **16** | **多数是"缺参数"的正常拒绝**，错误信息清晰可执行 |
| **flaky** | **1** | `add_workflow_node` —— 三轮结果不一致 |

## 🔴 真 bug（按严重性排序）

### B1 `delete_workflow_node` 缺参数时不报错（危险工具静默执行）
- 现象：`handler({})` **没有抛错** —— 而其余 7 个危险工具都会明确拒绝
  （如 `write_sheet`："需要 rows（二维数组）"）。
- 风险：**危险操作在参数缺失时没有拦住**，可能误改工作流配置。
- 建议：与其他危险工具对齐，缺 `id`/`node_id` 时**先校验再执行**。
- 待办：确认那次调用是否真的改动了配置（见下）。

### B2 `add_workflow_node` 偶发失败（3 轮结果不一致）
- 现象：同一个调用在三轮里结果不同 → 疑似**状态相关**（节点已存在？索引冲突？）
  或存在**竞态**（前端状态与后端配置不同步）。
- 建议：查 handler 里是否基于前端缓存的 `nodes` 生成 id；若是，改为以后端返回为准。
- 影响：agent 添加节点可能"时好时坏"。

### B3 `switch_model` 的错误信息没有把可选模型列出来
- 现象：`模型 'undefined' 不在可选列表里。可用：` —— **冒号后面是空的**。
- 而 `list_available_models` 是 **always-ok**（数据存在）→ 说明只是**消息插值漏了**。
- 建议：把可用模型拼进消息（这是小模型自我纠错的关键线索）。

### B4 无任务时的返回**不一致**
- `get_workflow_status` → 报错"任务不存在"；`get_eval_status` → 正常返回。
- 建议：统一口径（要么都返回 `{status:'none'}`，要么都报同一个错）。
- 影响：小模型对"没有任务"的判断不稳定（评测里已见"分析进度"被误判成训练状态）。

## 🟡 提升空间

### H1 参数错误信息总体很好，可复用为"提示模板"
16 个 always-fail 里绝大多数消息都**直接告诉下一步该调什么**，例如：
- `list_sheets`："需要 filename（先用 list_uploads 看已上传的 Excel）"
- `run_workflow`："paper 缺失：请先用 list_workflow_uploads 看有哪些论文"

→ 建议：把这种"错误 + 下一步"的写法**推广到全部工具**（目前 8 个危险工具里
`delete_workflow_node` 就没做到）。

### H2 工具→路由映射不一（可测试性债）
上一轮巡检发现 44 个工具里 **3 个（7%）** 无法用正则从 handler 里可靠抽出 URL：
`read_docx`（GET，模板串）、`delete_workflow_node`（PUT `/workflow/config`）、
`switch_model`（实为 `POST /vllm/switch`）。
→ 建议：handler 里的 URL 统一写法（都用 `${API_BASE}` 模板串），便于静态检查与测试。

### H3 危险/只读的划分要更严格
`read_docx` 被标成 **dangerous**，其实它是纯读；这会让用户多一次无谓确认。
建议复核 8 个 dangerous 标记是否都名副其实。

## ⚠️ 方法论教训（本轮踩到的）

1. **不要拿"会改状态的路由"当探针**：我用 `POST /vllm/stop` 做无害探测，
   **真的把 vLLM 停了**（已用 `/vllm/start` + model_path 恢复，24 秒）。
   教训：探测脚本必须先按"只读/副作用"分级，副作用路由永不自动调用。
2. **正则从 handler 抽 URL 不可靠**：第一轮巡检的结论（405/无路由）全是抽取错误的假象，
   改用"真调 handler"之后才看到真 bug。
3. **危险工具的"参数校验检查"本身要谨慎**：B1 就是这样被发现的，但也说明
   这类检查可能触发副作用 —— 发现 B1 后必须**立刻核对配置是否被改动**。
