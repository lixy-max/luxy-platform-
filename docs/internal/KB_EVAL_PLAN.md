### 1.3 具体缺口清单（实测代码）

| # | 缺口 | 证据 | 后果 |
|---|---|---|---|
| **K-1** | **入库无质量报告** ✗ | `upload_zip` / `ingest_folder` 只返回数量 ✓ 无文档级统计 ✗ | 不知道有多少空文档/超短块/重复块 ✗ |
| **K-2** | **无去重** ✗ | 同文件导两次 ⇒ chunk 翻倍 ✗ | 检索结果重复 ✗ 浪费 top_k ✓ |
| **K-3** | **无 PDF 提取清洗** ✗ | `_extract_file_text` 直接取文本 ✓ | 页眉页脚/页码/乱码混进向量 ✗ |
| **K-4** | **分块不分结构** ✗ | `split_text` 只按段落/句子 ✓ 不看 `#` 标题 ✗ | 跨章节切开 ✗ 语义断裂 ✗ |
| **K-5** | **chunk 参数不可调** ✗ | 硬编码 500/50 ✗（`split_text(chunk_size=500)` ✓） | 不同文档类型（论文/法规/代码）一个参数 ✗ |
| **K-6** | **无检索评估** ✗✗ | 全项目无 Recall/MRR/nDCG ✗ | **无法回答"哪个 embedding 更好"** ✗ |
| **K-7** | **无 chunk 预览** ✗ | 前端只能看总数 ✗ | 用户看不到实际切出来的片段长啥样 ✗ |
| **K-8** | **无元数据** ⚠ | 部分有 `source` ✓ 无章节/页码 ✗ | 检索结果无法溯源到章节 ✗ |

## 第二部分 · 开源方案调研（有限搜索 ✓）

| 项目/标准 | 做什么 | 能借鉴什么 | 引入？ |
|---|---|---|---|
| **[LlamaIndex](https://github.com/run-llama/llama_index)** | RAG 框架，各种 **NodeParser** | ⭐ **SentenceSplitter / MarkdownNodeParser / SemanticSplitter** 三种分块策略 ✓ | 思路 ✓ 不引框架（重 ✗） |
| **[RAGAS](https://github.com/explodinggradients/ragas)** | **RAG 评估框架** | ⭐⭐ **faithfulness / context_recall / answer_relevancy** 等指标 ✓ + 合成测试集 ✓ | ⭐ **核心借鉴** ✓ 自己实现精简版 |
| **[MTEB](https://github.com/embeddings-benchmark/mteb)** | embedding 模型基准 | 检索任务用 **nDCG@10 / Recall@100** ✓ | 借指标 ✓ |
| **[BEIR](https://github.com/beir-cellar/beir)** | 检索基准数据集/协议 | ⭐ **零样本检索评测协议** ✓（query→corpus→qrels ✓） | 借协议 ✓ |
| **[Chroma / sentence-transformers](https://www.sbert.net/)** | 已在用 ✓ | 已够用 ✓ | — |
| **BM25（rank_bm25）** | 关键词检索 | ⭐ **混合检索**（向量+BM25 ✓）通常比纯向量好 5-15% ✓ | 可选 ✓（30 行实现 ✓ 零依赖 ✓） |
| **[NeMo Curator](https://github.com/NVIDIA-NeMo/Curator)** | 语料去重/清洗 | MinHash 去重 ✓（同训练模块 ✓） | 借算法 ✓ |

### 调研结论
```
✓ 分块策略借鉴 LlamaIndex 的三种 parser 思路（结构感知 ✓）
✓ 评估体系借鉴 RAGAS + BEIR：
   · 指标: Recall@k / MRR / nDCG@k（IR 标准 ✓ 零成本 ✓）
   · 测试集: 从现有 KB 自动抽「问题→应命中片段」对 ✓
   · 对照实验: 同训练模块的 A/B 方法论 ✓（同数据集 × 换变量 ✓）
✓ 可选加 BM25 混合检索（30 行 ✓ 通常 +5~15% ✓）
✗ 不引入 LlamaIndex/RAGAS 框架（依赖太重 ✗ 我们自己实现精简版 ✓）
```

## 第三部分 · 方案（4 块 · 对应训练的 ①提示词 ②上传清洗）

### 3.1 块一：**KB 数据质量规范**（`docs/KB_QUALITY_SPEC.md` · 对应训练的 ①）
| # | 条款 | 判据 | 默认 |
|---|---|---|---|
| **B1** | chunk 长度 | 300 ≤ 长度 ≤ 800 字符 ✓（中英混合按 token 折算 ✓） | 500 |
| **B2** | chunk 重叠 | 50-100 字符 ✓（≤ chunk_size 的 20% ✓） | 50 |
| **B3** | **空/超短块** | < 20 字 ⇒ 丢弃 ✗ | 丢弃 ✓ |
| **B4** | **重复块** | 精确 hash 相同 ⇒ 去重 ✓ | 开 ✓ |
| **B5** | **近似重复块** | MinHash Jaccard ≥ 0.9 ⇒ 去重 ⚠ | 关 ⚠（需预览 ✓） |
| **B6** | **PDF 噪声** | 页码/页眉页脚/「第 X 页」/孤行 ⇒ 清洗 ✓ | 开 ✓ |
| **B7** | **结构感知** | markdown/标题 ⇒ 按标题切 ✓ 不跨章节 ✓ | 开 ✓ |
| **B8** | **元数据** | 每块必须带 `source` ✓ `section` ⚠ `page` ⚠ `chars` ✓ | 开 ✓ |
| **B9** | **语言一致** | 单库主语言占比 ≥ 80% ⚠（混合库提示 ✓） | 只提示 ✓ |
| **B10** | **向量一致性** | 所有块同一 embedding 模型 ✓ 维度一致 ✓ | 已有 ✓ |

### 3.2 块二：**入库前检测 + 一键清洗**（对应训练的 ②）

### 3.3 块三：⭐ **检索质量评估**（对应训练的 A/B 判分 ✓ **这是最大缺口**）

#### 测试集怎么来（零人工 ✓ 关键设计）
```
从现有 KB 自动生成「问题 → 应命中的块」对：
  ① 每个 KB 随机抽 20-30 个块 ✓
  ② 用【云模型或本地模型】为每块生成 1 个问题 ✓（"读这段回答：..."）
  ③ (问题, 块 id) = 一条 qrels ✓（标准 IR 格式 ✓）
  ④ 人工抽检 5 条 ✓（确认问题确实能由该块回答 ✓）
⇒ 每个 KB 得到 ~20-30 条测试用例 ✓（成本 ~5 分钟 ✓ 云端几乎免费 ✓）
⇒ 存到 data/kb_eval/{kb_name}.jsonl ✓ 可复用 ✓ 可扩充 ✓
```

#### 指标（IR 标准 ✓ 全自动 ✓）
| 指标 | 含义 | 目标 |
|---|---|---|
| **Recall@5** | 前 5 条里命中正确块的比例 | ≥ 0.8 ✓ |
| **MRR** | 正确块平均排名倒数 | ≥ 0.6 ✓ |
| **nDCG@10** | 考虑排序的检索质量 | ≥ 0.7 ✓ |
| **Hit@1** | 第一条就命中 | ≥ 0.5 ✓ |
| **MRR 波动** | 同查询跑 3 次是否一致 | 0（确定性 ✓） |

#### 对照实验（**同 A/B 方法论 ✓**）
| 实验 | 变量 | 预期 |
|---|---|---|
| **E1 embedding 模型** | bge-small-zh vs bge-m3（同 KB 同测试集 ✓） | bge-m3 通常更好但慢 ✓ |
| **E2 chunk_size** | 300 / 500 / 800（同库 ✓） | 不同文档类型最优值不同 ✓ |
| **E3 结构感知切块** | 开 vs 关 | 开应该显著更好 ✓ |
| **E4 清洗** | 开 vs 关 | 去 PDF 噪声应该 +5~10% ✓ |
| **E5 混合检索** | 纯向量 vs 向量+BM25 | +5~15% ⚠ |
| **E6 top_k** | 3 / 5 / 10 | 找到最优 ✓ |

⚠ 每次只改一个变量 ✓（P-59 教训 ✓）+ 同一测试集 ✓ + 配对比较 ✓

#### 后端接口
| 接口 | 作用 |
|---|---|
| `POST /kb/{name}/eval/build` | 自动生成测试集（LLM 出题 ✓） |
| `POST /kb/{name}/eval/run` | 跑评测 → Recall@k/MRR/nDCG ✓ |
| `GET /kb/{name}/eval/result` | 历史结果（可对比多次 ✓） |
| `POST /kb/{name}/eval/compare` | 两次结果配对比较 ✓（带 t 检验 ⚠ n 小则只报差 ✓） |

### 3.4 块四：**调整**（评测出来的结论 → 落到库上）
```
评测发现 bge-m3 更好 ⇒ 一键切 embedding（已有接口 ✓）
评测发现 chunk 800 更好 ⇒ 一键 rechunk（新接口 ✓ 建副本 ✓）
评测发现结构感知更好 ⇒ 默认开启 ✓
⇒ 「评估 → 调整 → 再评估」闭环 ✓（和训练的 A/B 一样 ✓）
```

## 第六部分 · 边界（不做的 ✗）

| 不做 | 理由 |
|---|---|
| ✗ 引入 LlamaIndex / RAGAS 框架 | 依赖太重 ✗ 自己实现 ~200 行够用 ✓ |
| ✗ 用 LLM 给每条检索结果打分（RAGAS faithfulness 全量 ✓） | 贵 ✗ 先用 IR 指标（零成本 ✓） |
| ✗ 自动改用户的知识库 | 永远建副本 `_clean` / `_eval` ✓ 不动原库 ✓ |
| ✗ 混合检索默认开 | 需先评估 ✓ 默认关 ✓ |

## 第七部分 · 一句话总结

```
现状: KB 的 L1 能力（分块/入库/检索/换模型）其实不弱 ✓
      但缺【质量规范 ✗ 入库检测 ✗ 清洗 ✗ 评估 ✗】—— 尤其是【完全不能评估检索质量】✗✗
方案: 4 块 = 质量规范 + 检测清洗 + 检索评估（Recall/MRR/nDCG + A/B 对照）+ 调整闭环
      与训练模块用【同一套方法论】✓（规范/检测/清洗/评估/调参）
工量: 12 小时 ✓ 4 阶段 ✓ 每阶段可验证 ✓
```
