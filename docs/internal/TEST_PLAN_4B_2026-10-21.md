## 三、诚实结论

```
✓ LoRA 命中率 87% → 93%（+6.7pp ✓ 方向为正 ✓）
✗ 但**统计不显著** ✗（只有 1 个不一致对 ✗ McNemar p≈1.0 ✗）
✗ **天花板效应再次确认** ✗（base 已 87% ✗ 没有提升空间 ✗）
```

### 为什么又是天花板（诊断 ✓）
```
✗ 4B 友好档 = **单工具直接查询** ⇒ 本来就简单 ✓ base 也能做 ✓
✗ 设计意图是"测工具调用能力"✓ 但 base 已经会了 ✓
⇒ 要区分"会不会"必须用**多工具/多步**任务 ✗
⇒ 但多步任务 4B 两个臂都做不出来 ✗（hard 档实测 ✗）
⇒ **4B 模型没有"中间难度"可测区间** ✗ ← 这是根本困境 ✓
```

### 已确认的三层事实（累计 ✓）
```
① 极简任务: base 87% ≈ LoRA 93%（天花板 ✗ 测不出 ✗）
② 中等任务（stability 档）: base 67% vs LoRA 63%（持平 ✗）
③ 复杂任务（hard 档）: base ≈ LoRA ≈ 0%（都做不出来 ✗）
⇒ **4B 模型上加 LoRA 没有可检测的收益区间** ✗
```

## 四、唯一出路

```
⚠ **换 7B 底座** ✗
  · 7B 能做 hard 档 ⇒ 有真实的"会不会"区分度 ✓
  · 7B QLoRA 需要 ~10-11GB ⇒ **3060 12GB 勉强** ⚠（4B 用了 10.6GB ✗ 7B 会 OOM ✗）
  · ⇒ 必须用 **5060 Ti 16GB** ⚠ ⇒ **要等用户不玩游戏**
  · 或 3060 + 更小 batch + gradient checkpointing + 更短序列 ⚠ 需试

⚠ 或者接受 4B 的现实:
  · 4B + LoRA 的项目定位 = **"让 4B 学会工具调用"** ✓（已实现 ✓ 0→1 质变 ✓）
  · 不是"提升任务成功率" ✗（4B 能力上限 ✗）
```
