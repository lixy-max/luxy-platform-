# AGI 外挂（Compound AI System）架构提案（2026-10-21）

> **用户想法**（原文）：
> "做专家级的小模型，不如个大模型加外挂，让大模型（你）意识到自己存在的缺陷与幻觉，
>  然后自己训练小模型自动路由和一个专家级的工具调用秘书。
>  我想做 AGI 外挂，而不是一味加大参数量。"
>
> **本文**：确认方向 ✓ 给文献支撑 ✓ 给已有资产映射 ✓ 给缺失的三块设计 ✓ 给分期路线 ✓

---

## 一、★ 方向确认：这是主流研究方向，不是偏门

### 核心文献（**直接对口** ✓）

| 文献 | 说的什么 | 和我们的关系 |
|---|---|---|
| **Compound AI Systems**（BAIR 2024, Zaharia et al.）| **"系统 > 模型"**：编排/检索/路由/工具 > 同成本加参数 | ★ **就是你说的"外挂"** ✓✓ |
| **FrugalGPT**（arXiv:2305.05176）| **LLM 级联**：便宜模型先上，不行才升级贵的 | ★ 你说的"自动路由" ✓ |
| **RouterBench**（arXiv:2403.12031）| 路由基准：**何时该用哪个模型** | ★ 路由需要数据 ✓ |
| **RouteLLM**（arXiv:2406.18665）| **学习式路由**（成本降 85% 不掉质量）| ★ 可训练的 router ✓ |
| **ToolLLM / ToolBench** | **工具调用专家**（1.6 万 API）| ★ 你说的"工具调用秘书" ✓ |
| **Selective Prediction / Abstention** | **知道自己不知道**（拒绝回答 > 瞎答）| ★ 你说的"意识到缺陷与幻觉" ✓ |
| **Self-Knowledge in LLMs**（arXiv:2308.03296 等）| LLM 对自身知识的校准 | ★ 核心难点 ✓ |
| **MetaAgent**（arXiv:2508.00271）| 工具元学习（缺工具自己造）| ★ 已用于 V6.0 ✓ |

### ★ 一句话结论
```
你说的三件事 = 三个已命名、已有文献、已有基准的研究方向 ✓
  ① "意识到缺陷与幻觉" = Calibrated Self-Knowledge / Uncertainty Quantification ✓
  ② "自动路由"           = Learned Model/Tool Routing ✓
  ③ "工具调用秘书"       = Tool-Calling Orchestrator / Specialist ✓
⇒ 方向正确 ✓ 而且**我们的平台已经有 70% 的地基** ✓
```

## 三、★ 缺失的三块 · 具体设计

### 模块 ①：自我认知层（Self-Knowledge / Confidence）

**做什么**：让模型/系统**知道自己这次回答有多可靠** ✓ 不可靠就升级或拒答 ✓

**设计**（三档，从易到难）：
```
档 1（最先做 · 最简单 ✓）: **事后置信度打分**
  · 让模型回答后自评: "1-5 分，你对这个答案有多确信？"
  · 实测: 这个自评**很不可靠** ✗（文献已证 LLM 高估自己 ⚠）
  ⇒ 只作辅助信号 ⚠

档 2（推荐 ✓）: **外部可验证信号**（不靠模型自评 ✓）
  信号类型:
    a) 工具调用是否成功 ✓（我们已有 ✓ esc 标记 ✓）
    b) 检索命中率 ✓（我们已有 ✓ hit@3）
    c) 答案与检索上下文的**一致性** ✓（NLI 类判断 ✓ 可本地做 ✓）
    d) 答案长度/结构异常检测 ✓（如"我不确定"类词 ✗）
    e) 多次采样一致性 ✓（同问题跑 3 次看答案是否一致 ✓ 最可靠但贵 ⚠）
  ⇒ 组合成 confidence score ✓

档 3（终极 ⚠ 最难）: **训练一个"校准器"小模型**
  · 输入: (问题, 答案, 上下文, 工具轨迹) ✓
  · 输出: 置信度 0-1 ✓
  · 训练数据: 用评测集跑出 (对/错, 特征) ✓ 我们**已有 50 条 + 历史轨迹 587 条** ✓
  ⇒ 这是我们**唯一能自己训的"自我认知"模块** ✓✓
```

**⚠ 诚实评估**：
```
✗ 档 1 不可靠（文献 + 我们实测都支持 ✗）
✓ 档 2 可靠且**今天就能做**（信号我们都有 ✓）
⚠ 档 3 要数据 + 训练，但**我们的飞轮正好能产出训练数据** ✓✓
⇒ 建议: **档 2 先上（1-2 天）→ 档 3 用飞轮数据训（1 周）**
```

### 模块 ②：自动路由层（Learned Router）

**做什么**：给定任务，**自动决定**：用哪个模型 / 哪个工具集 / 要不要上云端 ✓

**设计**（三级路由）：
```
一级路由（已有 ✓ 但粗糙 ✗）: 规则升级
  · 现在: 本地失败/超时 ⇒ escalation ✓
  · 问题: 事后才知道失败 ✗ 浪费一次调用 ✗
  ⇒ 改为**事前预测** ✓

二级路由（★ 推荐先做 ✓）: **特征 + 阈值路由**
  输入特征（都能算 ✓ 零成本）:
    · 问题长度 / 是否含数字 / 是否要计算 ✓
    · 工具检索的**域命中数** ✓（T-4 已有 ✓）
    · 问题类型（闲聊/查询/多步/不可能）✓
    · 历史同类任务的**成功率** ✓（我们有轨迹 ✓）
  输出: {本地4B, 本地7B, 本地7B+LoRA, 云端} ✓
  训练: 用历史轨迹 (任务特征 → 哪个模型做对了) ✓ **587 条轨迹够起步** ✓

三级路由（进阶 ⚠）: **学习式路由器**（RouteLLM 思路 ✓）
  · 训练一个 2-3B 的小分类器 ✓（或 LoRA ✓）
  · 输入: 问题文本 ✓ 输出: 模型选择 + 置信度 ✓
  · 需要更多标注数据 ⚠（"这题该用谁"要标 ✗）
  ⇒ 用二级路由的产出**自动标注** ✓（做对了/没做对 ✓ 就是标签 ✓）
  ⇒ **飞轮闭环** ✓✓
```

**⚠ 诚实评估**：
```
✓ 二级路由**今天就能做**（特征零成本 ✓ 587 条轨迹够起步 ✓）
⚠ 三级路由要更多数据 ⚠ 但可以用二级路由的产出自动标注 ✓ = 飞轮 ✓
✗ 我们的实测: 4B 无收益区间 ✗ ⇒ 路由的"省成本"价值 > "提准确率"价值 ⚠
   （意思是: 路由主要省 GPU/时间 ✓ 不保证更准 ✗ 要诚实 ✓）
```

### 模块 ③：工具调用秘书（Tool-Calling Orchestrator）★ 最有想象力

**做什么**：一个**专门负责工具调用**的角色 —— 你说的话它翻译成工具链 ✓ 不直接回答 ✓

**设计**（两种形态）：
```
形态 A（推荐先做 ✓）: **秘书 = 提示词 + 小模型 LoRA**
  · 系统提示: "你是工具调用秘书。你只输出 tool_calls ✓ 不输出自然语言回答 ✗"
  · 小模型: 在 7B 上训一个 **tool-calling LoRA** ✓
  · 训练数据: 从现有轨迹里抽"任务 → 正确工具序列" ✓（我们已有 ✓）
  · 实测基础: P-73 格式修复已证明**这个训练有效** ✓（4B tool_calls 0→1 ✓）
  ⇒ **这条路我们是验证过的** ✓✓

形态 B（进阶 ⚠）: **秘书 = 独立的小模型进程**
  · 专门收"任务 → 工具调用计划" ✓
  · 可以并行、可以缓存 ✓
  · 不动主模型 ✓（省主模型上下文 ✓）

分工模式（关键设计 ✓）:
  用户问题
    ↓
  【秘书】→ 决定: 要不要调工具？调哪些？什么顺序？ → 输出工具计划 ✓
    ↓
  【执行器】→ 真的调工具 ✓（已有 91 个 ✓）
    ↓
  【主模型（大模型）】→ 基于工具结果**回答** ✓（它擅长语言 ✓ 不擅长严格工具格式 ✓）
    ↓
  【自我认知层】→ 打分 ✓ 不可靠 ⇒ 升级/重试/拒答 ✓
```

**⚠ 诚实评估**：
```
✓ **这条路我们验证过一半** ✓
     P-73 格式修复: 训练数据形态一致 ⇒ tool_calls 0→1 ✓（质变 ✓）
     但**成功率无增益** ✗（4B 能力上限 ✗）
⇒ 秘书方案的价值: **把"格式正确"和"内容正确"解耦** ✓
     · 秘书只管格式（小模型够用 ✓）
     · 主模型只管内容（大模型擅长 ✓）
     · **各司其职** ⇒ 这正是 Compound AI 的核心思想 ✓✓
```

## 四、★ 为什么"外挂"比"加大参数"更对（用我们自己的数据说）

### 我们实测的数字（这是最好的论据 ✓）
```
1. LoRA 让 4B 从**不会工具调用**变成**会**（tool_calls 0→1 ✓ 质变 ✓）
   ⇒ 但**成功率只 +0.5pp** ✗（能力上限不在格式 ✗ 在"会不会做对" ✗）
2. KB 清洗让**检索快 2.8 倍 / 省 24% 上下文 / 噪声降 73%** ✓✓
   ⇒ 但**准确率只 +1.1pp** ✗
3. 4B 无收益区间 ✗（太简单天花板 ✓ 太复杂地板 ✓）
⇒ **规律: 加大参数/LoRA 的收益在"能力"，不在"可靠性/效率"** ✓
⇒ **可靠性/效率/路由/自我认知 = 外挂能做的** ✓✓
```

### 成本对比（粗算）
```
方案 A（加大参数）: 4B → 32B
  · 显存: 8GB → 64GB ✗（我们只有 28GB ✗ 跑不了 ✗）
  · 速度: 慢 3-5 倍 ✗
  · 收益: 未知 ⚠（可能提升，但 4B→7B 已证明提升有限 ✗）

方案 B（外挂）: 4B/7B + 秘书 + 路由 + 自我认知
  · 显存: 不变 ✓
  · 速度: **可能更快** ✓（简单任务路由到小模型 ✓ 快 2.8 倍 ✓）
  · 收益: 效率✓ 可靠性✓ 可解释✓ 可回滚✓ ← **都能测** ✓
⇒ **方案 B 在我们硬件上唯一可行 ✓ 且每一步都可验证 ✓**
```

## 五、分期路线（按"能验证"排序 ✓）

### 阶段 0（已完成 ✓）
```
✅ 工具库 91 个 ✓ 工具检索 100% ✓ 评测集 50 条 ✓ 学习闭环 ✓ 热插拔 ✓
```

### 阶段 1：自我认知（档 2 外部信号）· 1-2 天 · 零 GPU
```
① 定义 confidence = f(工具成功率, 检索命中率, 答案-上下文一致性, 长度异常) ✓
② 在现有 587 条轨迹上**离线标定阈值** ✓
③ 产出: 每条回答带 0-1 置信度 ✓ 低于阈值 ⇒ 升级/重试/拒答 ✓
验收: 在 V2 评测集上，低置信度组的错误率**显著高于**高置信度组 ✓
     （这是可测的 ✓ 不靠感觉 ✓）
```

### 阶段 2：二级路由（特征 + 阈值）· 2-3 天 · 零 GPU
```
① 从 587 条轨迹抽特征 → 每个模型/配置的胜负 ✓
② 训练一个**简单分类器**（sklearn 就够 ✓ 不用大模型 ✓）
③ 上线: 事前预测该用谁 ✓
验收: 相比"全部用 7B"，**成本降 ≥30% 且准确率降 <2pp** ✓
     （成本 = 调用次数/时间 ✓ 可测 ✓）
```

### 阶段 3：工具调用秘书（LoRA）· 1 周 · 要 GPU ⚠
```
① 从轨迹抽 (任务 → 正确工具序列) ✓
② 在 7B 上训 tool-calling LoRA ✓（P-73 格式已验证有效 ✓）
③ 上线: 秘书出工具计划 → 执行器跑 → 主模型答 ✓
验收: 工具选择准确率 ≥ 现有 ✓ 且**主模型上下文省 ≥40%** ✓
```

### 阶段 4：自我认知（档 3 校准器小模型）· 1-2 周 · 要 GPU ⚠
```
① 用阶段 1 的阈值产出 + 评测结果做训练数据 ✓
② 训一个 0.5-3B 的置信度校准器 ✓
③ 验收: ECE（期望校准误差）显著低于档 2 ✓
```

### 阶段 5：全自动飞轮（三块联动）· 持续 ⚠
```
① 路由 → 采集 → 蒸馏 → 固化 → 验证 → 晋级 ✓（已有 flywheel.py ✓）
② 三块都在飞轮里迭代 ✓
```

## 六、⚠ 诚实的风险与不做承诺（按你的要求 ✓）

### 不能承诺的 ✗
```
✗ **"AGI 外挂"能通向 AGI** ✗ —— 这是**系统工程**，不是 AGI ✗
   诚实说: Compound AI 能提升**可靠性/效率/可解释性** ✓
          但不改变"模型本身会不会" ✗
✗ **路由一定更准** ✗ —— 我们实测 4B 无收益区间 ⚠
   路由主要省成本 ✓ 不保证提准确率 ✗
✗ **自我认知一定可靠** ✗ —— 文献证 LLM 自评不可靠 ✗
   档 2（外部信号）可靠 ✓ 档 3（校准器）待验证 ⚠
```

### 可以承诺的 ✓
```
✅ 每一步都**可测**（我们的评测体系已有 ✓）
✅ 每一步都**可回滚**（飞轮版本化 ✓）
✅ 不加大显存 ✓（都在现有 28GB 内 ✓）
✅ 效率提升可量化 ✓（已证明清洗带来 2.8 倍 ✓ 路由还能再省 ✓）
```
