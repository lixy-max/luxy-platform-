## 3. 调用次数分布：成功 vs 失败

| 分组 | 轨迹数 | 总调用 avg / p50 / max | 报错调用 avg / max | read+glob+grep avg / p50 / max | 回合数 avg / p50 |
|---|---|---|---|---|---|
| **成功**（final 非空 & rc=0） | 143 | **8.61 / 7 / 30** | 1.23 / 5 | **2.61 / 1 / 16** | 5.51 / 5 |
| **失败**（final 为空） | 33 | **26.30 / 23 / 55** | 2.76 / 8 | **12.52 / 11 / 33** | 14.67 / 14 |
| 失败-其中超时（rc=-9） | 31 | 27.55 / 24 / 55 | 2.84 / 8 | 13.03 / 11 / 33 | — |
| 失败-其中非超时（rc=1） | 2 | 7.00 / 7 / 10 | 1.50 / 3 | 4.50 / 4.5 / 6 | — |
| 超时但有稿（rc=-9 & final 非空） | 29 | 19.48 / 24 / 37 | 1.62 / 6 | 7.00 / 6 / 17 | — |
| 有工具报错但出稿（n_err>0 & final 非空） | 91 | 12.70 / 11 / 37 | 2.45 / 6 | 4.66 / 4 / 17 | — |
| 自造探测物（用了 write/kb_create 等） | 40 | 23.30 / 22.5 / 47 | 2.00 / 8 | 7.67 / 6 / 22 | — |

**结论：失败显著更"重"。** 总调用 **3.05 倍**（26.30 / 8.61），只读深挖调用 **4.8 倍**（12.52 / 2.61），回合数 **2.66 倍**（14.67 / 5.51）。失败不是"调错一次就死"，而是"**越失败越使劲挖，挖到墙**"——报错调用的涨幅（2.76/1.23 = 2.2 倍）远小于只读调用的涨幅（4.8 倍），说明增量主要来自"换着花样再读一遍"，而不是"在同一个报错上反复撞"（原样重发只有 2 条）。

### 超时到底是什么被切（关键机制，脚本 section 10）

| rc | 轨迹数 | 回合数 avg / p50 / max | 工具调用 avg | ms min / p50 / max |
|---|---|---|---|---|
| 0（成功） | 143 | 5.51 / 5 / 21 | 8.61 | 60828 / **60856** / 61034 |
| -9（超时） | 60 | **13.72 / 14 / 32** | 23.65 | 100001 / **100011** / 100094 |
| 1（短臂） | 6 | 3.50 / 3 / 6 | 4.83 | 19985 / **29988.5** / 29993 |

- `ms` 是**量化预算标记**，不是自然耗时：143 条 `rc=0` 全部落在 60.83–61.03s（200ms 内），60 条 `rc=-9` 全部落在 100.00–100.09s。所以不要用 `ms`/`step` 估 agent 速度，用**回合数**衡量工作量。
- `rc=-9` 与 `diagnostics=['stderr: [reflect] 超时']` **完全一一对应（60/60）**。
- 但 `rc=-9` 组里只有 **4/60** 是"最后一步还是工具调用"——也就是说**绝大多数不是死在 agent 的工具循环里，而是死在收尾的 reflect 阶段**。
- 因果链因此是：**深挖 → 回合数从 5 涨到 14 → 撞满 100s 预算 → reflect 阶段被切 → 31/60 连已经写好的 final 都没留下**（29 条侥幸留稿但整轮判死）。

**额外发现（运行器层面，非工具层）**：reflect 超时应只丢 reflect 结果，不应把已产出的 final 一起作废。同一批 60 条里 29 条有稿、31 条无稿，差别只在"答案有没有在被切之前落盘"——这 31 条空产出是可以直接靠运行器修复挽回的，与本报告的工具层结论互相独立。

## 4. 结论：每一类该补什么（三选一 + 证据）

| 处置 | 覆盖类（表 A） | 条数 | 占比(209) |
|---|---|---|---|
| **该补工具返回的信息** | 类 2a + 2b + 类 4 | 72 | 34.4% |
| **该补引导文案** | 类 1 + 类 3 + 类 6 | 66 | 31.6% |
| **真的缺工具** | 类 5 | 4 | 1.9% |
| 成功对照组（无需处置） | 类 7 | 67 | 32.1% |

### 类 1 名字猜错（11 条 / 5.3%）→ **该补引导文案**

**证据（排除"缺信息"与"缺工具"）**：报错文本**已经把答案说全了**——"paper_lora_call 只能调用【文档/表格类】工具…工作流等各有【独立工具】，应直接调用，不要经过 call…名字通常是 `paper_lora_` 开头的近似名，例如训练列表是 `paper_lora_train_list`"。信息一点不缺，可是 `paper_lora_call` 仍被调用 13 次、失败 12 次。
**判断**：这是**事前引导缺失**——正确规则只存在于"失败之后"的返回里，没有进入工具描述/system prompt（知识库 `10_tool_catalog.md`、`60_synonyms.md` 里有，但没有出现在调用决策发生的地方）。
**建议**：在 `paper_lora_call` 的**工具描述**里写死"禁止用于 workflow/train/kb/vllm 类，请直接调用对应的 `paper_lora_*` 工具"；同时给 `paper_lora_call` 的报错加**最近似合法名候选**（fuzzy）——但这是次优，引导前置才是主因。

### 类 2a/2b 空产出（32 条 / 15.8%，含落在类 1 的 1 条则共 33）→ **该补工具返回的信息**

**证据**：这 33 条里 **31 条（93.9%）是撞 100s 墙**；空产出组平均 **26.30 次调用**（成功组 8.61）、只读深挖 **12.52 次**（成功组 2.61）。而"挖"的**触发点**是可定位的：`paper_lora_list_datasets` 已返回 `name/path/size/mtime/lines/sample_task`，但**没有返回字段 schema、也没有任何一条样本正文**，而任务要求"说明它们各自适合训什么类型的能力"——agent 无法从 size 推出能力类型，只能去 `read` 文件正文；`read` 因路径解析报 `E:\home\luxy\...` 失败，于是改换路径形态继续试，直到墙。
**判断**：不是缺工具（`paper_lora_list_datasets` 就是对的工具），也不是纯文案问题——是**第一次返回的信息量不足以支撑任务**。
**建议**：在 `paper_lora_list_datasets` 的返回里补 **`messages` 的 key 列表 / 首条样本（截断 ~500 字符）/ roles / 估算 token 数**。同类问题还有 `paper_lora_train_list` 返回 `{"tasks": []}`：无法区分"从未训练过"和"记录随重启丢失"，agent 只能去翻磁盘（见类 3）；建议补 **持久化路径 + 该文件是否存在 + 历史累计条数**。

### 类 3 挖矿超时（26 条 / 12.4%）→ **该补引导文案**

**证据**：类的样例是**4 次调用、零报错、答案也写出来了**，仍然被 100s 墙切掉。超时组平均 13.72 回合（成功组 5.51），而失败增量集中在"换角度重查"：`paper_lora_kb_query` 共 209 次、`paper_lora_kb_info` 25 次。任务措辞本身在鼓励重复探测——含"（第 2 轮，请换一种验证角度）"的 137 条超时率 31.4%，不含的 72 条 23.6%（**+7.8pp**；但措辞与任务类型相关，只能算弱证据，不作为主论据）。
**判断**：信息不缺（零报错）、工具不缺（查询都成功），缺的是**"够了就收"的停止纪律**与**验证深度上限**。
**建议**：引导文案里加预算纪律——"找到能支撑结论的最小证据集就收尾；每个任务最多 N 次同类查询；'换一种验证角度'不等于'再查一遍同样的库'"。同类：给 `paper_lora_kb_query` 的返回头部附一行"本次命中 Top-k，库内共 M 个 chunk / 是否已覆盖"也可减少重复查询，但这属于第 1 项手段。

### 类 4 报错/找不到后未换路（40 条 / 19.1%，最大类）→ **该补工具返回的信息**

**证据**：**194 次路径形态错配 = 全部 314 次报错的 61.8%**，涉及 57 条轨迹；`read` 121/532 报错、`glob` 73/258 报错。报错原文：`Error: cannot read "E:\home\luxy\paper_lora_project\training_data\dimensions_cov_v1.jsonl": not found` —— 工具把 WSL 绝对路径 `/home/luxy/...` 解析成了 Windows 路径 `E:\home\luxy\...`，**报错里既没说"这是路径形态问题"，也没给可用的替代形态**，于是 agent 依次试 `/home/...` → `\\wsl.localhost\...` → `\\wsl$\...`，每种形态都再失败一次。
**为什么不是"真的缺工具"**：读取能力**已经存在且能用**——`pwsh` 621 次调用里 616 次成功（`wsl.exe`/`wsl -e bash -lc` 可以读 WSL 文件），4 次失败全是"想提权被沙箱拒"。所以缺的不是能力，是**报错信息没有把 agent 导向那条已经通畅的路**。
**建议**：`read`/`glob`/`grep` 报错时补三件事——(1) 说明"该路径被解析到了 Windows 驱动器，本工作区文件在 WSL 里"；(2) 直接给可用形态示例 `\\wsl$\Ubuntu-24.04\home\luxy\...` 或 `pwsh -Command "wsl -d Ubuntu-24.04 -- cat <path>"`；(3) 回显解析后的绝对路径，让 agent 立刻看到 `E:\home\luxy` 这个畸形结果。这一条修复的报错面最大（61.8%）。

### 类 5 自造探测物（4 条 / 1.9%；标签口径 40 条 / 19.1%）→ **真的缺工具**

**证据**：`write` 34 次 + `edit` 3 次（21 条轨迹自写文件），`kb_create` 8 次/7 条（自建 `probe_*` 知识库、注明"用完可删"），`create_sheet`/`write_sheet` 10 次；标签口径 40 条（19.1%）在工作区留下了自己的产物，平均 23.30 次调用（成功组 8.61）。典型行为：为了"读 JSONL 首条样本"而写一个 Python 脚本再用 `pwsh` 跑（`E:\WSL\_r8\extract_final_report.py`）。
**判断**：这是唯一**能力真空**——现有工具链里没有"按结构读本地数据文件（JSONL/XLSX/JSON）前 N 行 / 取字段名"的只读工具，`read` 又会路径错配，所以 agent 只能用"写脚本 + 跑脚本"这条昂贵且留下垃圾的绕路。补返回信息解决不了（每次的结构和字段都不同）。
**建议**：新增一个只读工具（例如 `paper_lora_peek_file`）：入参 `path / rows(默认 3) / fields_only`，返回字段名 + 每字段类型 + N 行截断样本，路径按 WSL 语义解析。它能同时消解类 2（数据集内容）、类 4（部分读路径）和类 5 三处需求。

### 类 6 其它失败（29 条 / 13.9%）→ **该补引导文案**

**证据**：异质但成分明确——4 条 `rc=1` 且**零工具报错**（3 次调用、答案正常，疑似运行器/模型侧退出码，**不是 agent 失败**）；3 条 `missing required property`（如 `kb_query` 漏 `kb_name`）；4 条沙箱被拒（`pwsh` 试图提权跑 `wsl -e bash`）。后两类都是**工具用法纪律**问题，不是信息缺失、也不是能力缺失。
**建议**：引导文案写明"必填参数清单"与"不要尝试提权/不要在 Windows 侧递归读 WSL 路径（用 `\\wsl$` 只读形态）"；同时对 4 条 `rc=1` 无报错样本，建议在运行器侧核实退出码语义（本节不做断言）。

### 类 7 成功对照组（67 条 / 32.1%）

只用手册点名的 2–5 个 `paper_lora_*` 工具、5 个回合内收尾（avg 8.61 次调用、只读深挖仅 2.61 次、零报错）。**"工具能一次答清"的任务就是成功的那批**——这从正面印证了上面三条处置方向：把第一次返回做够（类 2/4）、把纪律写进引导（类 1/3/6）、把结构读取补齐（类 5）。
