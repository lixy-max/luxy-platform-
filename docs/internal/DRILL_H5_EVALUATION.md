## 二、评估结论

### 2.1 一句话判断

**drill_v1p 没有可测增益** ✗ —— 写操作率 `5% → 5%`（Δ=0）✓ 工具调用率甚至 `45% → 40%`（Δ=−5，**但在 n=20 下属噪声** ✗ 不能读成"变差" ✓）。
**P-6 的提示瘦身也没有提升工具使用率** ✗（`45% → 45%`）。
**真正有变化的是"云接手率"** ✓（`40% → 65% → 80%`）—— 那是平台修复（质量闸门）的结果，不是 LoRA 的 ✓。

### 2.2 这个结果**符合预期**，不是失败 ✗

按 `LORA_DATA_AND_EVAL_GUIDE.md`：
```
§1.3 数据量↔优化量: 40 条样本 × 5 epochs = 25 步 ⇒ 远低于"能产生行为改变"的量级 ✓
§1.2 秩容量墙:      rank=8（<100 样本时的默认 ✓）对"50 个工具里选对"这种任务偏低 ✓
§2.2 我们踩的坑:    数据是"动作计划文本"✗ 而 agent 推理时要输出的是【直接 tool_call】✗
                   ⇒ 形态不匹配（下节详述 ✓ 这是最关键的一条 ✓）
```

### 2.3 ★ 最关键的根因：**训练标签的形态和推理时的输出形态不一致** ✗✗

```
训练数据里 gpt 字段是: {"intent":"act","plan":["create_docx"],"should_ask":false,"deliverables":[...]}
   ⇒ 模型学到的是"用 JSON 描述我打算怎么做" ✗
推理时 agent 需要的是: 直接产出原生 tool_call（function calling 结构 ✓）
   ⇒ 两者不是同一种输出 ✗ ⇒ 模型即使学会了"计划"，也不会变成"动手" ✗
⇒ 佐证（实测）: arm2 里它确实在 P1-01 动了手（那条任务的数据形态最接近 ✓），
   但 P1-10/P1-34 这类"导出/写文档"任务仍然是 0 工具 + 转云 ✗
```

### 2.4 第二个根因：**云接手解决"说法"，解决不了"动手"** ✗

抽查 arm2 里被云接手的两条：
```
P1-34「给我写个 docx」→ 云的答案: "我无法直接生成 docx，但可以给你内容 + Python 脚本…" ✗
P1-10「把结果导出来给我」→ 同类 ✗
```
⇒ 因为云接手走的是**纯对话端点**（`/chat/completions` ✓ 无工具 ✗）
⇒ **任务依然没完成** ✗ —— 只是从"本地答错"变成"云端给你讲解" ✗
⇒ 这是**新的平台缺口（P-15）**：云接手应当也能调工具（或至少把自己产出的 `PLAN` 交给平台执行 ✓）

### 2.5 平台修复带来的**真实收益**（与 LoRA 无关 ✓ 但要记清楚）

```
✓ 知识库从"永远长不大"变成【真的在积累】(0 → 30 块 ✓ P-1 ✓)
✓ 用户短口气的任务不再被当垃圾丢掉（保留率 95.7% ✓ P-2 ✓）
✓ 失败不再静默: 云接手率 40% → 80% ✓ 且答案都带"说明 + 替代方案"（质量闸门 ✓ F2/A1 ✓）
✓ 训练从"跑不完"变成"能跑完"（25/25 步 ✓ P-3/P-5/P-12 ✓）
✓ 不合格数据不再白烧时间（前置闸门 ✓ P-4 ✓）
```

## 四、诚实声明（避免误读）

```
1. n=20/臂 ⇒ 写操作 3→1→2 这种差异【不显著】✗ 只能说"无可测增益"，不能说"变差了" ✗
2. 本次只测了"是否动手"这一维度 ✗ 没有做判官式质量打分（计划里的判官环节未执行 ✗）
3. arm1/arm2 的 system 完全相同 ✓ 所以 Δ(arm2−arm1) 只反映 LoRA ✓（对照设计成立 ✓）
4. 但 arm0→arm1 同时含【提示瘦身】与【平台修复（质量闸门）】两个变量 ✗
   ⇒ "云接手率 +25" 主要来自质量闸门 ✓ 不是提示瘦身 ✓ 这点已在 §2.5 说明 ✓
5. 训练数据是从 part1 任务**应调工具**推导的监督 ✗ 不是"真实正确轨迹" ✓
   ⇒ 严格说它是"应该怎么做"的标注 ✓ 不是"实际做成过"的示范 ✓（这也是 §2.3 的一部分 ✓）
```
