## 2. 规则公平性（逐条挑刺）

### 【高1】4 条「不可能」题反向评分：不做 = 满分，照做 = 15 分

**规则位置**：`parse_tasks` L65-67（`expect_no_tool`）+ `score_machine` L124-129（relevance 分支）+ L146-147 + L158-159。

`expect_no_tool` 一旦为真，只要"没调工具 + msgs 长度>10"就给 **30/30**；没卡片再给 **15/15**；`needs_artifact=False` 再给 **10/10**；无 error 再给 **5/5** ⇒ 合计 **60/60**。

**实测反例（用判分器自己的 `score_machine`，同一题 P1-48）**：

| 行为 | 机器分 |
|---|---|
| **A) 照 P1-48 验收点1「先 `list_knowledge_bases` 核对库名是否存在」** | **15.0/60**（工具选择 0，动作 0） |
| **B) 一个工具都不调，直接说"做不到，没有这个库"** | **60.0/60（满分）** |

**为什么这是硬伤**（不是"设计如此"）：任务书 `docs/DRILL_TASKS_PART1.md` 里 P1-48 验收点1 白纸黑字要求**先调用工具核对**；P1-49 要求"说明上传/解析支持的格式范围"、P1-50 要求"说明产物落点"——这些都要动工具。但 `parse_tasks` L66 的 relevance 判定**只看 kind 标签里有"不可能"**（那条 cat 正则实测一条都没命中，是死代码），从不看验收点是否要求查证。
⇒ **越听话越吃亏**，且 4 条题 = 4×60 = 240 分白送，直接进 mean。

**同类但更隐蔽的还有「边界」题**：P1-43 验收点1 明确"若库里确实没有任何产出，须**先追问确认**，不许凭空编"，但 `expect_no_tool=False` ⇒ 正确追问 = **10.0/60**（工具 0 + 动作 0 + 落地 5 + 干净 5），判 ❌。P1-41/42 的"先问清再写"同理。**这与判分器自己的 docstring L10 自相矛盾**——它写着"给出的工具都不该用时……不是'0 工具=失败'✗"，但只在"不可能"标签上执行了这条原则。

**改法**：见 §4-改法1。

### 【高2】老记录没有 `ui_cards`/`exec_tools` ⇒ 工具选择、动作完成恒为 0（60 条被冤判）

**规则位置**：`tools_of` L98-107 只认 `exec_tools` → `ui_cards`，**没有第三级回退**；`cards_of` L106-107 只认 `ui_cards`。

**实测**：

| tag | 有 `ui_cards` | 有 `exec_tools` | 工具选择得分合计 |
|---|---|---|---|
| arm1 / arm2 / v2r32 | **0/20 / 0/20 / 0/20** | 0/20 | 每批 30.0（**只来自 P1-48 那条 relevance，其余 19 条全 0**） |
| arm1p / v2r32p | 0/20 | 0/20 | 30.0（同样） |
| arm1s | 4/6 | 4/6 | **115.1** |

⇒ `arm1 (mean 9.6) vs arm1s (mean 34.6)` 看起来"新臂好 3.6 倍"，实际是**字段缺口**：arm1 那 20 条根本没有卡片数据，`s1+s2=45` 全额丢掉。这不是模型差，是**量具没上**。

**而且证据是白丢的**：老记录里 `msgs` 文本其实带卡片、`tools`/`uniq_tools` 字段也有值——

| tag | `tools` 非空 | `uniq_tools` 非空 | **msgs 里能解析出卡片** |
|---|---|---|---|
| arm1 | 9/20 | 9/20 | **13/20** |
| arm2 | 8/20 | 8/20 | 8/20 |
| v2r32 | 5/20 | 5/20 | 5/20 |

例：arm1 的 P1-01 `tools=[]`，但 msgs 里有 5 张 `❌ create_workflow_config / use_workflow_config` 卡片，完全可还原。判分器一个都没用。
⚠ 注意：arm1r 的 `tools` 字段里存的是 `['✅','❌']`（图标被当工具名）⇒ 回退时必须过白名单，不能直接信 `tools`。

**改法**：见 §4-改法4。

### 【高3】聚合不分层、不配对：mean 不可比，且被不可能题抬高

**规则位置**：`aggregate` L179-200（`scored` 全量进分母，无 `kind` 分层）+ `score_all` L266（`run = rs[-1]`）。

**(a) 不可能题计入 mean/合规率**（任务书 §0 明说"4 条不可能……不计入成功率分母（单列）"，判分器没实现）：

| tag | mean | **剔除不可能后 mean** | 差额 |
|---|---|---|---|
| arm1s | 34.6 | **30.0** | −4.6 |
| v2r32s | 28.2 | **22.3** | −5.9 |
| arm1r | 19.6 | **12.0** | −7.6 |
| v2r32r | 17.3 | **9.2** | −8.1 |

**(b) 不同 tag 跑的子集不同，mean 直接对比是错的**：

| tag | 题数 | 跑了哪些题 |
|---|---|---|
| arm1 / arm2 / v2r32 / arm1p / v2r32p | 20 | 01,03,05,07,08,10,13,15,17,18,20,23,26,28,31,34,36,43,45,48 |
| arm1r / v2r32r / **arm1s** / v2r32s | 6 | **01,05,07,10,34,48**（全是配置编辑/产出/不可能的难例） |
| arm1p2 / arm1p2b | 9 / 14 | 前 9 条 / 前 14 条（截断，非随机） |

可配对的臂只有同名后缀对（`arm1↔v2r32`、`arm1p↔v2r32p`、`arm1r↔v2r32r`、`arm1s↔v2r32s`，共同题分别 20/20/6/6）。**报告的 mean 是各跑各的子集，不能横着比**；应改成"按共同 task_id 配对求差"。

**(c) `rs[-1]` 只取最后一次**：同 tag 同 id 多次跑时，取最后一次而非最好/平均/首次。当前无重复（0 组），但后台跑批继续追加后会出现——同一个臂重跑一次差的结果就能拉低整臂。

**改法**：见 §4-改法1（分层）+ 改法4（配对）。

### 【高4】`类目` 被当成"必调集合"，但它其实是"能力/可选工具族"

**规则位置**：`parse_tasks` L61-64 把 `类目`/`前置` 里所有反引号名收进 `tools`；`score_machine` L136-139 用它算 recall（必调）。

`docs/DRILL_TASKS_PART1.md` 的 `类目` 是"这条题练哪些能力"的标注，用 `·` 分隔**可替代/不该做**的工具。三个实测反例：

| 任务 | 类目原文 | 判分器当成必调 | 正确做法 | 实得 |
|---|---|---|---|---|
| **P1-44**（边界·文本编辑） | `replace_in_file` · `replace_text` · `set_lines` · `set_lines_in_file` | **4 个都要调** | 4 个是**互斥方法**，选 1 个改完即可 | 只用 `set_lines_in_file` 改完全对 ⇒ **16.50/30**（recall 上限 1/4） |
| **P1-46**（边界·GPU 冲突） | `list_running_tasks` · `get_vllm_status` · `start_training` · `run_eval` | **4 个都要调** | 验收点3 明确"给串行排期、**不硬并行**" ⇒ 后两个**不该执行** | 只查两项+给排期（完全正确）⇒ **21.00/30** |
| **P1-01**（可完成） | 7 个工具 | 7 个都要调 | 中途 `list_workflow_nodes` 是合理探查 | 实执行 3 个 ⇒ 13.14/30（precision 反噬） |

另：`P1-01` 里 agent 第 1 轮就调了 `list_workflow_nodes`（合理探查），被 precision 扣分——**合理探索被当噪声**。

**改法**：见 §4-改法2。

### 【高5】`类目` 抽取把**节点名**当成工具：`finaloutcome`

**规则位置**：`parse_tasks` L54-64（`grab('前置[^:：]*')` + 反引号正则，**没有工具白名单过滤**）。

P1-07 expect = ['create_workflow_config', 'delete_workflow_node', 'finaloutcome', 'list_workflow_nodes', 'use_workflow_config']

### 【中6】落地性（10 分）靠文本正则，既会被"嘴上说"骗过，也会误杀真产出

**规则位置**：`_ARTIFACT_HINT` L113 + `score_machine` L154-162。`has_hint` 在整个 `msgs` 里搜 `(.docx|.xlsx|.json|.md|已生成|已保存|已创建|...)`。

**真实数据假阳性（不是构造的）**：P1-01 实况是 4 次 `create_workflow_config` 全失败、**没有任何 docx 产物**，落地性却拿了 **10.0/10**——因为后端错误信息里出现了 `.json` 字样（`文件名不合法：必须以 .json 结尾`）。命中：`['.json']`。

**构造反例（P1-34，需要 docx）**：

| 行为 | 落地性 |
|---|---|
| 只说不做，文本写"已生成 output.docx"（无卡） | 0/10 |
| **跑了 1 个无关只读工具 + 文本写"已生成"** | **10/10（白拿）** |

**改法**：见 §4-改法3。

### 【中7】判官 prompt / 判分代码的三个洞

**规则位置**：`JUDGE_PROMPT` L204-221 + `judge_task` L224-251。

| 洞 | 证据 |
|---|---|
| ① `evidence` 只检查"非空且不含'未找到证据'"，**不检查它是否真出现在材料里** | 构造：验收点材料里啥也没有，判官引用 `已生成 /home/luxy/outputs/perfect_paper.docx（此句根本不在材料里）` ⇒ **判官分 8.0/40、ok=True** |
| ② `pass` 用 `x.get('pass')` 真值判断 | 判官输出 `{"pass":"false"}`（字符串）⇒ `bool("false")==True` ⇒ **照样算通过** |
| ③ 材料本身不可核验 + 被截断 | `result_blob` = 工具名 + 是否转云 + **`msgs[-4000:]`**。验收点却大量是"md5 未变 / 文件存在 / 节点真的写进克隆件 / docx 可解析"——**判官没有任何工具能核验，只能信模型自述**；且 P1-07 的 msgs 长 **18736 字，前面 14736 字的证据判官看不到** |

附：`points` 每条分值 = 40/条数，实测只有 4 条题和 5 条题两种（4 条：38 题；5 条：12 题）⇒ 每题 10.0 或 8.0 分，颗粒度粗但可接受。

**改法**：见 §4-改法5。

### 【中8】转云一律扣 2.5，但转云可能是**正确**行为

**规则位置**：`score_machine` L164-169：`s4 = 5.0 if not escalated else 2.5`。

**影响面**：全库 `escalated` = **112/201 = 55.7%**（v2r32 18/20、arm2 16/20、v2r32p 15/20、arm1 13/20）。也就是说一半以上的记录被这一条扣分。

而任务书自己的机制里，本地模型做不了时转云接手是**设计好的兜底**（学习增强触发；P1-34 就是靠转云才产出 docx）。把"是否转云"当"干净度"扣分，等于**惩罚平台自己的兜底机制**，且与"任务做对没有"无关——P1-34 内容全对（30+15+10）只因转云从 60 变 57.5。

**改法**：见 §4-改法5（并入"干净度"重构）或单列：改成"转云不扣分；只有**转云后仍失败**才扣"。

### 【中9】`--judge` 开启但判官全部失败时，仍按 100 分制算合规 ⇒ 合规率假性归零

**规则位置**：`main` L361-368（`has_judge = judge is not None`，取自**工厂有没有 key**，不看判官实际成功率）+ `aggregate` L184（`_line = 70 if has_judge else 42`）。

**实测**：用"永远返回非 JSON"的 call_llm 跑 arm1s ⇒ `mean=34.6, compliance_rate=0.0%`。机器分不变，但阈值从 42 跳到 70，而分母满分只有 60 ⇒ **任何任务都不可能合规**。判官因网络/key 抖动全失败时，报告会显示"合规率 0%"而不是"判官不可用"，这会直接污染 LoRA 结论。

## 3. 判官 prompt 专项挑刺

`JUDGE_PROMPT`（L204-221）要求"必须引用实际结果里的原文作为证据；引不出来 ⇒ 判 false"——**方向对，但执行层没兜住**：

1. **"引用"没人校验**（中7-①）：prompt 里的要求靠模型自觉，`judge_task` L244-245 只做 `str(evidence).strip()` 非空 + 不含"未找到证据"，**不做 `evidence in result_blob`**。⇒ 判官可以编一段像模像样的证据拿分。
2. **行为性验收点判官能判，但状态性验收点判官判不了**：
   - 能判（行为/文本类）：P1-48「明确回答该库不存在」、P1-49「明确回答做不到」、P1-50「不得出现 huggingface.co 链接」——判官看文本即可。
   - **判不了（状态类）**：P1-01「默认配置 `workflow_config.json` 未改动（md5 不变）」「docx 在 outputs/ 存在且 `read_docx` 能解析」、P1-05「新节点真的写进克隆件」、P1-44「原件 md5 与改动前一致」。这类必须**用工具回查真实状态**（判分器现在完全没有回查能力），否则只能信模型的话 ⇒ 编造即得分。
3. **材料不足**：只喂 `msgs[-4000:]` + 工具名 + escalated。P1-07 长 18736 字 ⇒ 证据被砍 78%。而且 `msgs` 是"页面文本"，不含工具返回值（判分器没把卡片 result 喂给判官）。
4. **JSON 解析宽松**：`re.search(r'\{.*\}', raw, re.S)` 贪婪匹配 → 若模型输出带解释文字，可能截取到错误区间；`items` 缺项时按不过算（可接受），但 `pass` 的字符串布尔是硬伤（中7-②）。
5. **验收点与"机器段"重叠**：P1-48 验收点1 要求先 `list_knowledge_bases`，机器段却把"调了工具"判 0（高1）——同一题机器段和判官段**互相矛盾**，判官给 40 分也救不回来（机器段已封顶 15）。

**总结**：判官 prompt 的"必须引用证据"是**纸面规则**，执行层没有校验，且对"状态类验收点"结构性无能为力。40 分里有多少是"模型自述可信度"而非"任务完成度"，目前无法区分。

## 4. 五条改法（每条：位置 + 现规则 + 改成什么 + 为什么）

### 改法 1 ——【最高优先】不可能题改"行为分级"，并把统计按 kind 分层

- **位置**：`parse_tasks` L65-67；`score_machine` L124-129 / L146-147 / L158-159；`aggregate` L179-200。
- **现规则**：`expect_no_tool=True` ⇒ 不调工具=30，没卡片=15，无产物需求=10，无 error=5 ⇒ **60/60**；且这 4 条计入 mean 与合规率。
- **改成**：
  1. `parse_tasks` 给每题加 `scoring_mode`：`complete / boundary / impossible`（取 kind 标签），**不要**用 cat 正则猜。
  2. 不可能题的 tool_choice 改**三档行为判定**（用 `api_tools` 提出序列 + 是否有查证动作）：
     - 先查证（调了 `类目` 里的只读工具）**且**说明了"为什么不可能" ⇒ 30/30；
     - 未查证但正确说明不可能 ⇒ 20/30；
     - 硬跑写操作 / 编造结果 ⇒ 0/30。
     动作完成 15 分同口径（有查证动作且无 error 卡=15；无动作=8）。
  3. `aggregate` 增加 `by_kind` 分层（可完成/边界/不可能各报 n、mean、compliance），**主合规率分母剔除 impossible**（单列），与任务书 §0 一致。
- **为什么**：现状"不动手=满分、照做=15 分"是**方向性错误**，且 4 条题白送 240 分，会让任何臂的均分虚高 4.6–8.1 分（实测 arm1s 34.6→30.0、v2r32r 17.3→9.2）。这是最直接污染 LoRA 结论的一条。

### 改法 2 —— 工具期望集改"或"语义，并用真实工具白名单过滤

- **位置**：`parse_tasks` L54-64。
- **现规则**：`类目`/`前置` 里所有反引号名 ⇒ 必调集合（recall 分母），且不过滤非工具名。
- **改成**：
  1. 加载 `agent_kb/_tools.json` 的 52 个真实工具名做**白名单**，过滤掉 `finaloutcome` 这类非工具（白名单外的一律丢，且记一条 warn）。
  2. 把 `类目` 里 `·` 并列的工具视为**"或"集合**（能力族）：recall = 命中其中**任一**即 1.0，不再按个数摊。
  3. 对明确"择一执行/不该执行"的题（P1-44 的 4 个替换方法、P1-46 的 start_training/run_eval）**不参与 AST recall**，交判官按验收点判。
  4. precision 只惩罚"既不在 expect、也不在**只读探查白名单**（`list_*`/`get_*`/`read_*`/`query_*`）"的调用。
- **为什么**：P1-44 做对只能 16.5/30、P1-46 做对只能 21/30、P1-06 永久上限 25.5/30——三处都是"做对反被扣"，且都是 `类目` 语义被误读造成的。工具名错抽（`finaloutcome`）还会直接拉低 recall 分母。

### 改法 3 —— 落地性改成"执行证据 + 真实产物"，不再靠文本正则

- **位置**：`_ARTIFACT_TOOLS` L110-112、`_ARTIFACT_HINT` L113、`score_machine` L154-162。
- **现规则**：`needs_artifact` 由 expect 里是否有产物类工具决定；`has_hint` = 在 msgs 里正则搜 `.docx/.json/已生成...`；`has_hint and oks ⇒ 10 分`。
- **改成**：
  1. `has_hint` 不再单独作判据。落地分 = **产物类工具（`_ARTIFACT_TOOLS`）的 ok 卡片存在**（50%）+ **该工具返回体里出现真实路径/文件名**（30%）+ **后端回查该路径确实存在/可读**（20%）。
  2. 文本 hint 降级为"加分说明"，不再能独立拿分。
  3. 顺手修死项：`_ARTIFACT_TOOLS` 里把 `save_workflow_config` 换成 `create_workflow_config`（因为 `norm_tool` 会归一成后者）。
- **为什么**：P1-01 真实数据里 4 次失败、无产物却拿 10/10（错误信息含 `.json`）；反过来真 `write_docx` 成功但答案没提 `.docx` 却 0/10。这条判据同时**可被"嘴上说"骗过**又**误杀真产出**，是"落地性"最难自证的一段。

### 改法 4 —— 补数据源回退链，让老记录/缺卡片记录可评；工具选择用"提出"而非"执行"

- **位置**：`tools_of` L98-107、`cards_of` L106-107、`score_all` L266。
- **现规则**：只认 `exec_tools` / `ui_cards`；没有就一律空 ⇒ s1/s2 = 0。
- **改成**：
  1. `tools_of` 回退链（逐级）：`exec_tools` → `ui_cards` → `api_uniq_tools` → `api_tools` → `uniq_tools`/`tools`（**必过工具白名单**，因为 arm1r 的 `tools` 里存的是 `['✅','❌']`）→ **从 `msgs` 用 `(✅|❌)\s*([a-z_]\w*?)\s*\d+\.\d+s` 解析**（P-20 已验证该模式；arm1 有 13/20 条可解析）。
  2. **口径分离**：`tool_choice`（s1，BFCL 的 AST 匹配）应看**模型提出**的调用（`api_uniq_tools`/`api_tools`），而不是执行结果；`execution`（s2，动作完成）才看 `ui_cards` 的 status。
  3. `rs[-1]` 改为"同 tag 同 id 取最近一次，并记录 run 序号；报告里标注重跑"（或取 best/median 并显式声明）。
- **为什么**：60 条老记录（arm1/arm2/v2r32）现在 s1/s2 恒 0，均分 9.0–9.6 无法与有卡片的臂比较；而这些记录里 13/20 条 msgs 明明有可解析卡片、9/20 有 `tools` 字段，白丢。**修之前不能拿 arm1 与 arm1s 横向比。** 另外 BFCL 的 AST 口径本来就是判"模型该调什么/调了什么"，用"执行"代替"提出"在概念上就错位了。

### 改法 5 —— 判官加固 + 判官失败时降级，并重构"干净度"

- **位置**：`judge_task` L224-251；`JUDGE_PROMPT` L204-221；`aggregate` L184；`main` L361-368；`score_machine` L164-169。
- **现规则**：evidence 只判非空；`pass` 用真值；材料只喂 `msgs[-4000:]`；`has_judge` 取自工厂；转云一律扣 2.5。
- **改成**：
  1. **evidence 强校验**：`if str(ev).strip() and str(ev) in result_blob` 才算通过；否则判 false 并标 `evidence_not_found: true`。
  2. **`pass` 严格布尔**：`x.get('pass') is True`（拒绝 `"false"`/`1`/`"true"` 这类）。
  3. **材料补全**：喂"全部 `ui_cards`（名字+status+result 截断）+ 所有工具返回的关键字段 + msgs 的**结构化分段**（命中验收点关键词附近的窗口）"，而不是生硬截尾部 4000 字。
  4. **状态类验收点交给回查**：验收点里带"md5/存在/可解析/未改动"的，判分器应先跑只读回查（`list_workflow_configs` / `read_docx` / 文件 md5），把回查结果放进材料；回查不了的验收点**显式标 `unverifiable` 且不给分**，不要让判官替它猜。
  5. **判官失败降级**：`has_judge = (判官成功条数 / 应试条数) >= 0.9`；否则按 42 分口径算合规，并在报告里写"判官 N/M 失败，总分仅 60 上限"。杜绝"合规率假性 0%"。
  6. **干净度改为只扣"无效转云"**：`escalated` 且最终有 ok 产物 ⇒ 不扣；`escalated` 且仍失败/无产物 ⇒ 扣 2.5。理由：转云是平台设计好的兜底，全库 55.7% 记录被扣分不合理。
- **为什么**：判官 40 分是总分里最大的一块（40%），现在它能被伪造引用、字符串布尔和无证据自述刷分；而 `--judge` 一抖动就把合规率打成 0。这两件事都会让"LoRA 变好没有"不可信。
