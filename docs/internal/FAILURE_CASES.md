# 失败案例集

> 清单里把这一项标为"最稀缺的内容"。本文只收**真实发生过**的失败，
> 每条都写清：**现象 → 复现 → 根因 → 修法 → 如何防复发**。
> 不收"理论上可能出错"的假设。
>
> 时间范围：2026-10 的密集开发期。本文按性质分组，组内每条都是独立案例。
> （早先版本这里写过"共 N 例、分 M 组"，但每次追加新组都没同步更新，
>   反而变成一个会误导人的断言 —— 所以现在只列组，不写总数。）

## 一、前端"静默失败"（最伤用户：点了没反应，还不报错）

### F1 `onChatFileSelected is not defined`
- **现象**：聊天页上传文件，控制台报未定义函数，按钮无反应。
- **根因**：HTML 内联 `onchange="onChatFileSelected()"` 只能解析**全局**符号，
  而该函数定义在闭包里，不是 `window` 属性。
- **修法**：移除内联处理器，改在 `bindChatDropZone()` 里用闭包绑定。
- **防复发**：界面探针断言"页面里所有内联处理器都能解析到定义"。

### F2 状态变量未声明（`docFlowHeaderCache is not defined`）
- **现象**：参数面板渲染到一半抛 `ReferenceError`，整块界面不显示。
- **根因**：用了 `docFlowHeaderCache` / `docFlowDrag` 但**没声明**，靠赋值产生隐式全局；
  先读到就抛错。
- **修法**：把 `docFlow*` 系列状态统一**显式声明**。
- **防复发**：同一类错在本项目发生过三次（`docFlowDraft` → `docFlowDraft/Sel`
  → `docFlowHeaderCache/Drag`）—— 说明"靠赋值产生全局"这种写法本身就是隐患。

### F3 四个函数从未被定义 —— 而"检查"说是存在的
- **现象**：「➕ 添加步骤」等按钮点了没反应。
- **根因**：我此前的"补函数"检查用的是**字符串包含**判断，而**按钮的 `onclick`
  字符串恰好满足它** → 检查通过、函数其实从未创建。
- **修法**：程序化审计 —— 抽取页面所有 `on(click|change|input)` 引用的名字，
  逐个检查是否存在 `function <name>(` 定义；查出 4 处缺失并补齐。
- **防复发**：新增结构性测试 `editflow-inline-handlers-defined`，
  它用**函数定义 + 全局可调**判定，而不是字符串包含。
- **教训（重要）**：**"检查通过"不等于"事情做成了"**。假检查比不检查更危险。

### F4 弹窗标记整个不在文件里
- **现象**：点「➕ 添加步骤」不弹窗，**且不报任何错**。
- **根因**：`#add-doc-step-modal` 的 HTML **根本不在文件里**；
  函数取到 `null` 后直接 `return`，于是既不报错也不弹窗。
- **如何发现**：**这是我第一次用浏览器自动化探针时抓到的** ——
  DOM 探针直接给出 `✗ 添加步骤弹窗可见: false`。
- **修法**：把弹窗标记补回，插在 `</body>` 之前（确保是顶层可见元素）。
- **防复发**：探针把"关键弹窗可见"作为断言。

### F5 静默 catch 让失败隐形
- **现象**：节点库区域空白，但控制台没有任何 error。
- **根因**：相关 `try/catch` 用的是 `console.warn`，而探针只捕获 `console.error`。
- **修法**：把 4 处静默 `catch` 改为 `console.error`。
- **教训**：**降级日志的级别决定了自检能否看见问题**。

### F6 改提示词时用反引号，弄断模板字符串 —— 最严重的一例
- **现象**：用自然语言让 agent 做"论文编辑+导出"，它**一个工具都没调**（页面无工具卡片），
  却回答了一整篇「我已修改完成」「文件已保存至 E:\lora test pdf url\论文-编辑版.docx」——
  **而那个文件根本不存在**。控制台另有 `Unexpected identifier 'replace_text'`
  与 `setAgentMode is not defined`。
- **根因**：`buildAgentSystemPrompt()` 返回的是**反引号模板字符串**，我在里面插入提示词时
  用了 `` `replace_text` `` 这样的**行内反引号** → 提前闭合了模板字符串 → JS 语法错误 →
  整个 agent 模块加载失败。
- **为什么门禁没拦住**：前端断言全是**源码字符串匹配**（`/replace_text/` 照样命中），
  它**不解析 JS** → 370 项全绿，而 agent 实际已死。
- **修法**：提示词里改用「」或裸词，**永不使用反引号**。
  更重要的是补上**真正的语法门**：`tools/check_js_syntax.js` 把每段 `<script>` 交给
  Node 的 `vm.Script` 解析，并接进前端门禁（新增断言 `js-syntax-valid`）。
- **教训（本会话最贵的一条）**：
  1. **"门禁全绿"与"功能可用"是两件事** —— 字符串断言抓不到语法错误。
  2. **模型会在工具链断掉时"编造成功"** —— 它声称产出了文件，而文件不存在。
     所以**验收必须落到文件系统**（存在性 + 内容），不能只看回答。
  3. 在**模板字符串**里插文本时，反引号与 `${}` 是禁区。

## 二、盲目请求与占位符

### D1 `/docs/sheets?filename=%7B%7Bfile%7D%7D` 返回 400
- **现象**：加一个 `read_sheet` 节点后，控制台刷 400。
- **根因**：节点默认参数是 `filename={{file}}`（**运行时才替换**），
  而参数面板**立刻拿这个未解析的占位符去请求**真实接口。
- **修法**：只有**真实文件名**（不含 `{{`）才发请求；否则不下拉也不报错，只给提示。
  并给整个面板渲染包一层 `try/catch`，单字段失败不再打断整块界面。
- **防复发**：源码级断言"不得把占位符当文件名请求"。

## 三、写得出、读不回（读写不对称）

### W1 `write_docx(out_dir=E盘)` **谎报成功**
- **现象**：测试断言 `{"written": "e2e_result.docx", "exists": false}` ——
  返回里给了 `path`，但**那个文件根本不存在**。
- **根因**：导出逻辑**假设**产物在 `OUTPUT_DIR/<filename>`，而 `write_docx_new`
  实际用的是 `docs_out_path(...)` → 复制被静默跳过，却照样把 `path` 写进返回值。
- **修法**：逐个候选路径（返回的 `path` / `OUTPUT_DIR` / 项目内 `rglob` 兜底）找
  **真实产物**；找到才复制并置 `exported=true`；找不到写 `export_error` **如实报告**。
- **教训**：**"谎报成功"是最不能容忍的一类 bug** —— 它让调用方无法察觉。

### W2 `create_*` 能写到 E 盘，`read_*` 找不到
- **现象**：`create_docx` 成功写出到 `E:\...`，`read_docx` 报 404「文件不存在」。
- **根因**：读工具的输入解析来源太窄（只在 `uploads/` 找）。
  （同一根因更早还导致过 `add_toc` 找不到刚创建的文件。）
- **修法**：新增 `_resolve_input_file(name, out_dir, exts)`：
  `uploads → outputs → 指定目录 → 项目内按名兜底`；读工具全部改走它。
- **设计取舍**：**不**递归扫描整个 E 盘（太慢且有风险）→ 读 E 盘产物**必须传 `out_dir`**。

### W3 `_resolve_input_file` 解析出路径，却只把文件名传下去
- **现象**：修了 W2 之后**仍然 404**，而且错误信息退回成子函数自己的措辞
  （"可用 list_uploads 查看"），让人误以为补丁没生效。
- **根因**：`_ft_read_docx` 拿到解析结果后调用 `read_docx_text(src.name)`，
  而该函数内部**只认 uploads/** → 刚解析出的目录被丢掉。
- **修法**：不再二次转手，直接对**解析后的文件**读取
  （`_ft_read_docx` 用 python-docx、`_ft_read_sheet` 用 openpyxl）。
- **教训**：**"字符串包含式检查"与"只看错误消息"都会误导** ——
  要看**实际拿到的东西**（这里是 `src` 这个 Path 有没有被真的用上）。

## 四、内容处理里的真错误

### C1 `/uploads/text` 把 PDF 当纯文本读
- **现象**：agent 拿着乱码作答，同时上下文被撑爆 → `LLM 调用失败：vLLM 400`。
- **复现**：直接请求该接口，返回文本开头是
  `'%PDF-1.7\n\n4 0 obj\n<<\n/Filter /FlateDecode\n/Length 24203\n>>\nstream\nxIH,Sp"...'`。
- **根因**：兜底逻辑是"优先同名 `.txt`，否则读原文件本身"，而该 PDF **没有 `.txt` 副产物**
  → 直接按 utf-8 读了 PDF 二进制。
- **修法**：按格式分流 —— 文本类直读（并加防呆：开头是 `%PDF` 或控制字符比例 >5%
  判为二进制并报 415）；`.docx` 走抽取器；`.pdf` 用 `pdfplumber`（回退 `pypdf`）
  **真抽取**，抽不到就诚实报 422「可能是扫描件，请走 OCR 路径」。
- **附带**：还修过一次"文件不存在"与"格式不支持"混在一起导致 `sample.txt` 报 415 的问题。

### C2 `add_toc` 把目录页搬到文档末尾去了
- **现象**：新文档前几段是「四、下一步 / 三、风险 / 二、进展 / 一、背景」，
  「目录」反而排在后面。
- **根因**：用 `body.findall(w:p)[-N:]` 取"刚添加的段落"再搬到最前 ——
  实际抓到的是**原文档末尾的小节标题**。
- **修法**：创建段落时**保留对象引用**，搬运这些对象本身（不按位置切片），
  用 `reversed()` 依次 `insert(0)` 保持顺序；返回值加 `placed_first` 供自检。
- **附带坑**：目录域指令 `'TOC \o "1-3" \h \z \u'` 里的 `\u` 被 Python 当 unicode 转义
  → 必须用**原始字符串** `r'...'`。这次被语法门控在提交前拦住。

### C3 `format_fix` 不合并行内多余空格
- **现象**：规整后仍输出「这是一段   有很多空格的文字」。
- **根因**：只处理了行尾空白，没处理行内。
- **修法**：加三条规则 —— 行内连续空格压成一个；中文之间的空格去掉（PDF 复制常见）；
  中文标点前的空格去掉。

### C4 长文一次性处理：89 秒且输出重复
- **现象**：3 万字一次性翻译耗时 **89 秒**，译文重复。
- **根因**：模型被超长输入拖垮。
- **修法**：`_split_chunks`（按段落边界切块，块内超长再按句号硬切）+
  `_doc_llm_long`（逐块调用，带"上一块结尾"做衔接；`condense`/`terminology` 用 reduce 再合并）。
  覆盖 translate / polish / proofread / condense / terminology / structure_fix，
  返回值带 `chunks`。

### C5 润色把口语改成文言腔
- **现象**：输入「这个东西吧，就是有点那个…」，输出
  「此事虽有诸多不便，然终究不可忽视」。
- **根因**：提示词只说"更书面化"，模型**越界**改变了语体层级。
- **修法**：提示词明确"**不改变语体层级**，原文是口语就仍是口语"。
  复测输出：「这个东西嘛，确实有点问题，反正你懂的，我们得把它理一理才行。」

## 五、我自己的操作失误（流程纪律）

### P1 `git add -A doc_flows/` 把**用户的**未跟踪文件卷进提交
- **现象**：用户自己的 `doc_flows/doc_flow_new.json` 被提交进仓库。
- **修法**：`git rm --cached` 退回未跟踪（**文件本体与内容一字未改**）。
- **纪律**：改动范围**必须显式列路径**；哪怕"只加一个目录"也不行 ——
  那个目录里可能有用户自己的东西。

### P2 视图与真相分歧：快照 / 仓库不同步导致回归
- **现象**：早期出现两次"改好的东西又没了"（`NODE_OPTIONAL_FIELDS`、
  `NODE_TYPES_FIXTURE` 丢失）。
- **根因**：我同时维护"仓库"与"Windows 侧快照"两份，改了一份以为另一份也变了。
- **纪律**：**仓库是唯一真源**；改动后 `cp` 到快照并 `diff` 复核。

### P3 用花括号匹配正则替换 JS 函数 → 过度匹配，破坏无关函数
- **现象**：模块级 patch 把 `setAgentMode` 弄坏。
- **修法**：从 HEAD 恢复，改用安全边界（"下一个 4 空格缩进的 `function`"）。
- **纪律**：**不要用花括号匹配正则去替换 JS 函数体**。

### P4 中文字符串里嵌引号（本会话共 5 次）
- **表现**：`SyntaxError: invalid syntax`（中文引号 `"..."` 在双引号字符串里）、
  `\u` 被当 unicode 转义、`\\'` 嵌套转义。
- **修法**：中文引号统一用 `「」`；需要反斜杠时用原始字符串。
- **纪律**：改 Python/Shell 脚本**先过 `py_compile` / `bash -n`**，再跑真实入口。

### P5 提交脚本"只打印不门控"
- **现象**：测试失败（甚至语法错误）的提交照样进了仓库。
- **修法**：本次起 —— **门控退出码**：脚本类改动先语法检查，
  再跑一次真实入口，**退出码为 0 才提交**。

### P6 把带 `SyntaxError` 的脚本提交出去
- **现象**：`ab395b4` 带着语法错误进了仓库，`make repro` 直接报错。
- **根因**：P4 + P5 叠加。
- **修法**：修好并补上语法门控；同时做了一次**全仓 Python 语法体检**（结果无问题）。

## 六、测试自身会骗人（这一组教训最贵）

### T1 负向用例判反：5 个正确行为被报成失败
- **现象**：空文本、不存在的文件、越权目录等用例全部报 FAIL。
- **根因**：测试框架把"抛出异常"一律记为 FAIL —— 而这些用例**本来就该抛异常**。
- **修法**：三类结果分开记 —— `PASS` / `CHECK`（行为与预期不同，需人判断）/
  `FAIL`（非预期异常）；负向用例用 `expect_raise` 标记，抛预期异常记 **PASS**。

### T2 打桩不忠实：桩把负向用例放过去了
- **现象**：打桩自检时，「空文本应报错」报 FAIL（说"预期报错但成功了"）。
- **根因**：桩"无论输入什么都返回文本"，**没有保留真实实现的入参校验**。
- **修法**：桩里保留同样的校验（空输入照样抛 400）。
- **教训**：**桩必须忠实于真实实现的契约**，否则自检结论不可信。

### T3 "刚好不到阈值"这个错我犯了三次
- **现象**：分块相关断言（`chunks >= 2`）连续误报；第三次的 `assert` 直接把整轮打断，
  等于 `make doc-test` 被我自己弄坏。
- **根因**：我一直在**估算**测试输入的字数（1300 / 4028 / 4588，阈值 2500），而估算总是不准。
- **修法**：改成 `while` 循环拼接到明确超过 7000 字，并保留自检 `assert`。
- **意外收获**：那个 `assert` **三次都拦住了我** —— 它证明自检写得值。

### T4 测试里用错函数名
- **现象**：`AttributeError: module 'lora_manager' has no attribute 'read_sheet_new'`。
- **根因**：我猜了函数名（真实是 `read_sheet_summary`）。
- **修法**：按真实名字取，并在取不到时**打印候选列表**。

### T5 用 `tail` 管道缓冲住输出，等了 50 分钟看不到进度
- **现象**：后台跑测试台，`job_output` 一直空白。
- **根因**：我把命令管道给了 `tail -60` → **输出被缓冲**，不到结束不吐。
- **修法**：长任务**直接写日志文件**，再用另一个信息源看进度（进程是否在、
  产物时间戳是否在推进）。
- **纪律**：**长任务一律后台跑 + 先报进度**，不在工具调用里前台干等。

## 七、视觉/前端杂项

### V1 箭头"太大了"，而我第一次的修改**等于没改**
- **现象**：用户反馈"还是大，基本没动"。
- **根因**：`markerUnits` 的**默认值就是 `strokeWidth`**，它会把 `markerWidth`
  **再乘上线宽**。我把 9 改成 6 并显式写了 `markerUnits="strokeWidth"`（**等于默认值**）
  → 实际从 `9×1.8=16.2px` 变成 `6×1.8=10.8px`，看起来几乎没变。
- **修法**：改用 `markerUnits="userSpaceOnUse"` 让数值成为**绝对像素**（稳定 7px）。
- **纪律**：**别改"等于默认值"的属性**；视觉改动也要**可测量**
  （用探针读属性算出有效尺寸，而不是"我觉得改小了"）。

### V2 导航项"不可见"
- **现象**：探针点不到「📝 编辑工作流」。
- **根因**：应用默认停在对话页，二级导航**要先进「工具」标签才显示**。
- **教训**：自动化要先走**用户真实路径**（先点父标签），
  不能假设目标元素一直可见。

### V3 启动脚本阻塞 360 秒 + venv 路径假设错误
- **现象（第一次）**：一键启动"卡住"，用户反馈"要这么久"。
  **根因**：拉起 vLLM 后**前台轮询 180 次 × 2 秒 = 最多 360 秒**。
  **修法**：底座改为**异步** —— 提交请求 + 快速探测一次，未就绪就立即返回并提示进度。
- **现象（第二次）**：`✗ 找不到 Python（python3）` 直接退出，一键启动形同虚设。
  **根因**：只试了 `$ROOT/.venv`，而本机 venv 在 `/home/luxy/.venv`；
  找不到就退回 `python3`，而非交互 shell 里 `python3` 不在 PATH。
  **修法**：多候选探测（`$VENV → 项目 .venv → ~/.venv → 项目 venv → PATH`），
  并**打印实际使用的 Python 路径**。
- **纪律**：**路径类假设必须打印出来给自己看**。

| **假设代替验证**（路径/落点/顺序/阈值） | W1 W2 W3 C2 T3 V3 |
| **测试自身不可信** | T1 T2 T3 T4 T5 |
| **转义与字符串坑** | P4 P6 C2 |
| **流程纪律缺失** | P1 P2 P5 |

**一句话**：本项目里最贵的 bug **不是算法错**，而是
**"看起来成功了，其实没有"** 和 **"检查说没问题，其实检查是假的"**。
对应的解药也很明确：**结构性测试**（不是字符串包含）+ **可测量的断言**
（不是"我觉得"）+ **三类结果分开记**（PASS/CHECK/FAIL）+ **关键路径必须有探针**。

## 八、云 API 打通战役（用自然语言驱动 agent 做真实文档编辑，7 轮才成功）

> 任务：让内置 agent 编辑一篇论文并导出 Word（作者改 luxy、单位改个人、校对、术语、结构、引用核查）。
> 前 7 轮**全部失败**，每轮都暴露一层不同的问题。这一组是**最有价值的素材**：
> 因为**每一次失败看起来都像"模型太笨"，实际有 13 次是代码问题**。

### G1 `write_docx_new` 逐字符成段
- **现象**：导出的 Word 有 **2410 个段落**，前 3 段是「一、引言」「一」「、」—— 每个字一段。
- **根因**：`for para in paragraphs`，而 `paragraphs` 传进来是**字符串** → 逐字符迭代。
- **修法**：`isinstance(paragraphs, str)` 时先按换行拆段。
- **教训**：这个 bug **同时影响文档流程的导出**，而我此前"验证"只查了**文件存在**、没查**内容** ✗
  → 属于 F6 同一类（验证错对象）。

### G2 两个流式端点写死 8192 上下文
- **现象**：云模型上，任务还没开始就被截断（"最新一条消息超过上下文预算 8192 tokens，已截断"）。
- **根因**：`ctx_limit = get_vllm_max_model_len() if req.provider == "vllm" else DEFAULT_CONTEXT_LIMIT` ——
  **两处**都这么写；云模型一律按 8192 算，而系统提示含 33 个工具说明 + 任务本身。
- **修法**：统一改走 `chat_context()`，并为已知云模型建窗口表（deepseek-chat 65536）。

### G3 `chat_context` 不认带前缀的 provider id
- **现象**：后端 `/chat/context?provider=openai` 是 65536 ✓，但前端拿到的还是 8192。
- **根因**：前端传的是完整 id `openai:deepseek-chat`，后端精确匹配 `openai` 失败 → 回退默认。
- **修法**：先按 `:` 切出 provider 名；再从 id 里的模型名查窗口表。

### G4 上传内容注入取"最后一个"文件名
- **现象**：任务明确点名 `test1.txt`，agent 却一直在处理 `pdf1.txt`。
- **根因**：注入逻辑取 `fromText[fromText.length - 1]`（最后一个匹配），
  而我的任务文本末尾写了"注意：pdf1.txt 不是本次对象" → **恰好注入了 pdf1**。
- **修法**：改取**第一个**；并且 **agent 模式下不再预注入正文**（它有 `read_upload` 工具）。

### G5 agent 模式预注入正文
- **现象**：上下文被挤占、模型被带偏（见 G4）。
- **修法**：agent 模式下直接 `return null`（不注入），只在普通对话模式注入。

### G6 `MAX_ITER = 8` 半途而废
- **现象**：跑完术语统一就停了，正说着"现在规整标题层级"却没有下一次调用。
- **根因**：agent 循环上限 8 次，而文档流水线要 6+ 次工具调用 + 中间还有别的调用。
- **修法**：提到 24。

### G7 消息扁平化丢掉 `tool_calls`
- **现象**：云 API 400，模型"反复试探参数"。
- **根因**：`/chat/tools` 把消息压成 `{role, content}`，丢掉了 assistant 的 `tool_calls`
  与随后的 `tool_call_id` 对应关系 → 云 API 校验失败。
- **修法**：**原样透传**相关字段（role/content/name/tool_calls/tool_call_id）。

### G8 回填塞 `tool_calls: null`
- **现象**：同上（400），回合直接中断。
- **根因**：错误路径里写了 `tool_calls: call.__raw || null` → 显式 `null` 也不合法。
- **修法**：统一用一个 `pushToolResult(call, result, cloud, acc)`：
  云模型推 `tool` 角色 + `tool_call_id`，且前一条 assistant 必须带**同一个** `tool_calls`。

### G9 `json` 在本模块是别名 `json_lib` ★最隐蔽
- **现象**：云模型返回的 `arguments` 明明是合法 JSON 字符串，却全部落成 `{"_raw": "..."}`
  → 所有工具调用参数都解不开 → 工具全废。
- **根因**：模块顶部是 `import json as json_lib`，而我的解析器里写了 `json.loads`
  → 那里 `json` 不是标准库 → 抛异常 → 静默走兜底。
- **修法**：改用 `globals().get("json_lib") or globals().get("json")`。
- **教训**：**"函数在、参数在、返回值在，但语义不对"** —— 只有把中间值打印出来才能发现。

### G10 `condense_file` 把论文压成 8%
- **现象**：导出后标题/摘要/英文摘要整块消失，正文从 4777 字变 427 字。
- **根因**：模型自己挑了"精简"工具（它属于**改写**类，会大幅删内容），而我没有任何防护。
- **修法**：文件版语言工具加**缩短告警**（<60% 时返回 `warning`）+ 提示词硬约束
  「用户没要求压缩就禁止用 condense 类工具」。

### G11 工具参数 `required` 没标全 → 整行被删
- **现象**：导出的 Word 没有 luxy、也没有原文那行，正文还短了一截。
- **根因**：我生成的 tools schema 里 required 只标了 `filename/source/title`，
  模型于是**只给 find 不给 replace** → 而 replace 缺省=空串 → 等于把那行删掉。
- **修法**：按工具语义给全 required（`replace_in_file` 必须 find+replace）；
  并且在实现里**缺 replace 时不再默默删行**，而是返回 `need_replace` 提示。
- **教训**：**"默认值"就是契约的一部分** —— 危险默认值（删除）必须显式要求。

### G12 工具内部的模型调用写死本地 ★用户发现的
- **现象**：用户看 GPU：**占用满**，"可能循环出问题了，没有全走 api"。
- **根因**：`_doc_llm()`（所有 `*_file` 工具内部那一次模型调用）注释就写着
  "按前端的同一条路径调本地 vLLM" → **写死 127.0.0.1:8000**。
  于是 agent 在云上跑 ✓ 而每个工具内部都在本地 4B 上算 ✗ → GPU 打满、慢得离谱。
- **修法**：用 `ContextVar` 传递"本次请求选定的模型"，前端 `callDocTool` 带上 `model`；
  `/docs/tool` 设置并在结束时复位。实测：云路由校对 7.5 秒，**GPU 前后都是 4%（完全没碰）**。
- **教训**：**"我在用云"不等于"整条链路都在用云"** —— 要逐层核对真正发起请求的地方。

### G13 Markdown 标题没转成 Word 标题样式
- **现象**：模型说"标题层级规整为 ##/###"，但导出的 Word 里 **Heading 数为 0**。
- **根因**：`structure_fix` 输出 Markdown，而 `write_docx_new` 把每行都当普通段落写。
- **修法**：识别 `#{1,6}` 行并用 `add_heading(level=...)`。修后 **Heading 17 个**（1/2/3 级正确）。

### G14 分块标记被模型回显进正文
- **现象**：`read_upload` 返回的正文开头是「【第 1/2 段，请只处理这一段】」，
  模型于是**反复读同一段**（13 次 read_upload、690 秒无产出）。
- **根因**：`_doc_llm_long` 在 prompt 里加的分块标记，被模型**回显**到输出里 → 写回文件成了正文。
- **修法**：加 `_strip_chunk_markers()`，在**所有返回路径** + **写文件之前**双重清洗。

### 本组总结
| 层 | 数量 | 例子 |
|---|---|---|
| **能力缺口**（真的缺东西） | 3 | G6 循环上限 / G10 缺防护 / G13 缺 Markdown 转换 |
| **契约错误**（能跑但语义不对） | 4 | G4 注入取错 / G7 G8 消息形态 / G11 危险默认值 |
| **环境/配置错误** | 3 | G2 G3 上下文预算 / G9 json 别名 |
| **"没全走对地方"** | 1 | G12 工具内部用本地 |
| **验证错对象** | 2 | G1 只验存在不验内容 / G14 标记污染 |

> **一句话**：13 次失败里 **13 次是代码问题**，只有 0 次是"模型太笨"。
> 而每一次都**长得像模型太笨** ✗ —— 这就是为什么"先怀疑自己、用测量定位"是唯一靠谱的路。

## 九、干净环境 / 一键安装暴露的问题（只有"从零装"才看得见）

> 背景：本机开发时一切正常，但"全新环境安装"这条验收项一跑，
> 立刻抓到一个**发布即崩**的 bug。这类问题的共同特征是：**开发机上永远复现不了**。

### H1 `requirements.txt` 缺 `python-multipart`（做手术级别的发布阻断）
- **现象**：干净 venv 装完 requirements.txt 后跑测试 ——
  `Ran 544 tests ... FAILED (errors=13)`，比正常的 699 **少了 155 个**，
  4 个测试模块直接 `unittest.loader._FailedTest`。
- **根因**：`ImportError: python-multipart 缺失` →
  `lora_manager.py:858 @app.post("/loras/upload")` —— FastAPI 注册**文件上传路由**时必须
  有 python-multipart，否则**整个模块导入失败**。
  而 `requirements.txt` 是**扫描 import 反推**生成的 —— 本项目从不 `import multipart`，
  所以生成器**永远看不到它**。本机 venv 是历史上手工装过，才一直没暴露。
- **影响**：新用户按文档装完 → **后端根本起不来**（不是某个功能坏，是整个服务死）。
- **修法**：① `requirements.txt` 显式加 `python-multipart==0.0.20` 并注明原因；
  ② `scripts/gen_requirements.py` 加 `IMPLICIT_DEPS` 白名单，重新生成也不会丢；
  ③ **CI 加 `fresh-install` job**：只按 requirements.txt 装 → `import lora_manager` → 跑全测。
- **教训**：**"依赖靠扫描 import 反推"必然漏掉隐式依赖**。
  只要项目里有"框架要求的运行时依赖"，就必须有一道"干净环境导入"的检查。
- **验收**：修后干净 venv `Ran 699 tests OK`；本机环境不受影响（仍 OK）。

### H2 一键安装的幂等性（这条是设计对了，记录一下）
- `install.sh` 重复运行不会破坏任何东西：venv 复用、**已存在的 settings.json 不覆盖**
  （实测 md5 前后一致）、目录缺失才建、端口占用只提示不杀进程。
- 意义：安装脚本"可重复运行"是硬要求 —— 否则用户第一次失败后不敢再跑第二次。

## 十、agent 用错参数：工具"有信号却不说话"（2026-10-11 实测）

> 背景：这是一次**真实用户测试**暴露的。用户让 agent 用「通用论文分析工作流」分析
> `B.docx`，agent 正确产出了采购清单报告，然后用户说「保存到 e 盘」——
> agent 选了 `export_docx(source="result_20261011_192602.json")`，把**工作流结果的 JSON**
> 整坨导成了 Word ✗。用户打开文件才发现不对，改口要 Excel 才拿到正确产物。

### I1 `export_docx` / `write_docx` 会把"一整坨 JSON"当正文写成 Word
- **现象**：导出的 Word 里是 507 段 JSON —— `"source_file": "…", "log": [ "[input_paper]…"`，
  **标题层级 0 个**，唯一的 Heading 是 `{`（左花括号）。
- **证据链**（全部可复现）：
  - 工具返回值：`{"title": "{", "chars": 49354, "paragraphs": 507, "exported": true}`
    —— 标题就是 JSON 的第一个字符，**工具已经拿到这个信号了** ✗
  - 时间线：`19:26:02` 工作流产出 `result_*.json` → `19:27:11` 那个 JSON 被导成 `.docx` ✗
  - 核查 5 个已有文档流程，**没有一个会这么干** → 是 agent 手工把 JSON 文件名
    塞进了 `source`（`export_docx` 的语义是"把某个**文本**文件导出成 Word"）。
- **根因**：**工具对"输入明显不对"这件事保持沉默** ✗
  - `_ft_export_docx` 读文件 → 取第一行当标题 → 交给 `write_docx_new` 逐行写段，
    全程没有任何"这内容像不像正文"的判断；
  - 返回 `exported: true` + `note: "已导出到 E:\"` → agent 据此报告"✅ 已成功导出" ✗。
  - 同类前例：早先 `condense` 把 4777 字压到 427 字也一声不响（已加告警）；
    `write_docx_new` 逐字符成段（已修）。**这类"静默产出垃圾"是本项目最贵的一类 bug**。
- **影响**：用户拿到一个**打开才发现是垃圾**的文件；agent 还自信地宣称成功 →
  信任损失比功能缺失更大。而且 agent 不会自己回头检查（它只看返回值）。
- **修法**（唯一出口拦截，一处管三条路 `write_docx` / `write_docx_new` / `export_docx`）：
  1. 新增 `_looks_like_json_blob()`：内容以 `{`/`[` 开头，且
     ①含本工作台自己产出的 JSON 键（`"source_file"` / `"final_report"` / `"_meta"` /
     `"workflow"` / `"nodes"` / `"log":` / `"steps"` / `"trace"`），或 ②整体是合法 JSON；
  2. `write_docx_new` 开头：`paragraphs` 命中上述特征 → **400 拒绝** +
     给出三条可照做的替代做法（取 `final_report` / 先 `read_docx` / 另存为 `.txt`）；
  3. `_ft_export_docx` 额外拦 `source` 以 `.json` / `.jsonl` 结尾的情况（更早、提示更具体）。
- **为什么是"拒绝"而不是"只告警"**：告警会被 agent 忽略（它只看成功/失败）；
  而这里**没有任何正当用例**需要把 JSON 当正文写进 Word ✓
  （真要保留原始 JSON，另存为 `.txt` 即可 ✓）。
- **验收**（4 条全过，实测）：
  | 用例 | 期望 | 实测 |
  |---|---|---|
  | `export_docx(source=result_*.json)` | 400 + 明确指引，**不生成文件** | ✓ 拦住，E 盘无新文件 |
  | `write_docx(paragraphs=真正正文)` | 正常成功 | ✓ 4 段 |
  | `export_docx(source=test1.txt)` | 正常成功 | ✓ title 正确 / 4777 字 / 52 段 |
  | JSON 内容伪装成 `.txt` | 按**内容**也拦住 | ✓ 拦住（双层防护） |
- **教训**：**工具必须在"输入明显不对"时开口**。
  判据要挑那种"信号已经在手里但没人看"的 —— 这里是 `title == "{"`；
  同类信号还有：输出字符数骤降、段落数暴涨、标题层级为 0、纯符号标题。
  **判据要保守**（正常中文/英文正文不会以 `{` 开头），但**该拒就拒**。

## 十一、发布流水线自身的坑（"跑一遍才现形"，不跑永远不知道）

> 背景：v0.2.0 发布时第一次**完整跑通** `publish.sh` 流水线（打包 → 重解安装目录 → 同步快照 → 体检）。
> 结果一次性抓出 3 个问题，全都属于"**只有真跑才会现形**"——
> 单看代码、单跑测试都不会察觉，但会直接影响"发出去的包对不对"。

### J1 版本号只改了一半：包名还是旧版本
- **现象**：`VER` 改成 v0.2.0 后发布，产物却是 `paper-lora-workbench-v0.1.0.zip`
  —— 而且把 10-08 那份**上一版 zip 覆盖成了 v0.2.0 的内容**（文件名骗人）。
- **根因**：`publish.sh` 自己用了 `VER`，但调用 `bash scripts/make_release.sh` 时**没把参数传下去** ✗，
  于是 `make_release.sh` 用了自己的默认值 `v0.1.0`。**两个脚本各有一份版本默认值** = 两个真源。
- **修法**：`publish.sh` 改为 `bash scripts/make_release.sh "$VER"`；
  `make_release.sh` 默认值同步改 v0.2.0。**版本号只应有一个入口**。
- **教训**：文件名的正确性没人检查 —— 包名错了也能"成功发布"。
  **凡是拼出来的名字，都要在流程末尾断言一次。**

### J2 `publish.sh` 从来没有把 zip 拷出去（最严重的一条）
- **现象**：发布"成功"、体检也过，但目标目录 `E:\project test desktop\` 里**只有解压后的安装目录，
  没有 zip** ✗ —— 而 zip 才是"要发出去的那个文件"。用户拿到的是一堆散文件，不是分发包。
- **根因**：`publish.sh` 只做了 `zipfile.extractall(zip, DEST)`（解压），**从头到尾没有 cp zip** ✗。
  一眼扫脚本很容易把 `extractall(...zip..., DEST)` 那行误读成"拷贝 zip"（我复盘时就看错了 ✗）。
- **修法**：补 `cp -f release/<name>.zip "$DEST/"`，并**立刻 `cmp -s` 校验字节一致**，不一致就 `exit 1`。
- **教训**：**"成功"必须定义成"最终产物出现在最终位置且字节正确"**，
  而不是"命令退出码为 0"。缺少最后这一步断言，流水线越顺越危险。

### J3 体检脚本与 `git archive` 的 export-ignore 语义不一致
- **现象**：加了 `/agent_kb/_last_eval.json export-ignore` 后，包内**确实**排除了 ✓，
  但 `check_sync.sh` 报"应含 102 项 / 实含 101 项，缺少 `_last_eval.json`"✗。
- **根因**：`check_sync.sh` 用 `fnmatch(路径, 模式)` 比 pattern，而模式带前导 `/`、路径不带 ✗
  → 匹配失败 → 把**已正确排除**的文件算进"应有"。而 `git archive` 认带 `/` 的写法（路径锚定）。
  **同一个规则，两套实现，两种结果。**
- **修法**：`.gitattributes` 用无前缀写法（`git archive` 同样认）；
  同时 `check_sync.sh` 解析时 `lstrip('/')` 容错，以后两种写法都不误报。
- **教训**：**校验脚本必须与它要校验的那个实现同源**（这里：要么都用 `git archive` 语义，
  要么两边共用同一份解析）。体检结果不一致比不体检**更糟** —— 它会训练人忽略告警。

## 十二、服务端 / 前端的关键路径"从没被端到端跑过"

> 这一组是本项目**最贵的一课**：四条缺陷都很底层、一测就现形，
> 却藏了很久 —— 因为**云分支一直正常，把本地分支的问题全遮住了**；
> 而当时的做法是"用云绕开"，等于绕过了 bug 本身。

### L1 `/chat/tools` 的本地分支引用了不存在的变量（选本地模型必 500）
- **现象**：对话页选「（不挂 LoRA · 用当前底座）」或任何 `vllm:*` 模型，开 Agent 模式，
  一发言就失败；而选云模型（`openai:*`）一切正常。
- **复现**：`POST /chat/tools {"model":"vllm:base", ...}` → `HTTP 500`。
  后端日志：`NameError: name 'VLLM_PORT' is not defined`（`lora_manager.py` 本地分支）。
- **根因**：该分支写的是 `base = f"http://127.0.0.1:{VLLM_PORT}/v1"`，而 `VLLM_PORT`
  在项目里**根本不存在**（别处一律用 settings 的 `providers.vllm.api_base` 或写死 8000）。
  因为**本地分支从没被调用过**，所以从未暴露。
- **修法**：改用 settings 的 `providers.vllm.api_base`，兜底 `http://127.0.0.1:8000/v1`。
- **防复发**：`scripts/check_local_agent.sh` 静态检查"源码里不得出现未定义的 `VLLM_PORT`"，
  并用 `vllm:base` 真打一次 `/chat/tools`。

### L2 vLLM 启动时没开 function-calling（带 tools 的请求被拒）
- **现象**：修好 L1 后，本地请求不再 500，但返回的 `tool_calls` **恒为空**；
  直连 vLLM 则报 `400: "auto" tool choice requires --enable-auto-tool-choice
  and --tool-call-parser to be set`。
- **根因**：`vllm_manager.py` 构造启动命令时只带了 LoRA / 上下文 / 量化等参数，
  **没有** function-calling 相关开关 → vLLM 不接受 `tool_choice=auto`。
- **修法**：命令里加 `--enable-auto-tool-choice` 与 `--tool-call-parser hermes`
  （Qwen2.5-Instruct 的 tool 调用格式）。
- **防复发**：冒烟测试同时检查**源码**与**运行中进程的命令行** ——
  只改源码不重启 vLLM，是这类问题最常见的漏网方式。

### L3 前端对本地模型走"文本协议"，工具调用整体丢失
- **现象**：本地 agent 回答得像模像样，但**一个工具都没调**；问知识库数量时，
  它从「环境快照」里抄名单，还数错了（说 15 个，实际 17 个）。
- **根因**：前端 agent 循环里 `if (isCloudModel(...)) 用原生 function-calling
  else 用文本协议` —— 本地走的是文本协议，要求模型输出 `<tool_call>{...}</tool_call>`，
  而本地 Qwen **不打这个标记** → `parseToolCall` 返回 null → 整轮当成普通回答。
- **修法**：本地也走原生 function-calling（vLLM 已具备该能力，见 L2）。
- **防复发**：冒烟测试断言前端"本地也走原生"，并在注释里写明原因。

### L4 `buildToolsSchema` 只列文档工具，80+ 个 agent 工具没进 `tools`
- **现象**：即使前三项都修好，前端发出的 `/chat/tools` 请求里 `tools` 仍是空
  （或只含文档工具）→ 模型无工具可调。
- **根因**：`buildToolsSchema()` 只遍历 `DOC_TOOL_REGISTRY`（Word/Excel 那批），
  **完全没管** `AGENT_TOOLS`（`list_loras` / `list_knowledge_bases` /
  `query_knowledge_base` / `start_training` …）。
- **修法**：新增 `AGENT_TOOL_DOCS` 说明表 + `_agentToolSchema()`，并入 `buildToolsSchema()`；
  暴露的工具数从 0 变成 **88**。
- **防复发**：冒烟测试断言 `AGENT_TOOL_DOCS` 存在且被 `buildToolsSchema` 合并。

### L5（同类·交互层）`localhost` vs `127.0.0.1` 与"空 value 当没选模型"
- **现象 A**：页面里大量 `ERR_CONNECTION_REFUSED @ localhost:8001`，
  但同一批请求又有到达的 → **时通时不通**。
  **根因**：浏览器把 `localhost` 解析成 IPv6 `::1`，而后端只监听 IPv4。
  **修法**：`API_BASE` 与 `learn.js` / `rolechat.js` 全部改 `127.0.0.1`。
- **现象 B**：选「（不挂 LoRA · 用当前底座）」后点发送**毫无反应**。
  **根因**：该 `<option>` 的 `value` 是空串，而 `sendChat` / `sendAgentTurn` 都用
  `if (!sel.value …) return;` 判"没选模型"。
  **修法**：`value` 改成真实 model id `vllm:base`。
- **共同教训**：**"看起来能跑"和"真能跑"之间，隔着一整条端到端路径**。
  这两条都属于"代码本身没错，但用户第一步就走不通"。

---

## 十三、这一组教给流程的三条规矩

1. **有两条实现路径的能力，必须两条都端到端跑一次**。
   云分支的正常会长期掩盖本地分支的崩溃。
2. **改了源码 ≠ 生效**：vLLM / 后端 / 前端各自有"重启才生效"的边界。
   冒烟测试必须同时看**源码**与**运行中的进程/已加载页面**。
3. **别用"绕开"代替"修好"**：用云跑通 100 条任务，掩盖的是本地路径整条不通；
   产出再漂亮，也说明不了本地能力。
