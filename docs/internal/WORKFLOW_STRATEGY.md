# 工作流优化方向与可行性判断

> 定位：工作流是本项目的主干。核心目的是**让底座动态加载不同 LoRA，以高精度、低显存完成不同任务**；
> 现在的"论文处理"只是其中**一个简单模板**。
> 日期：2026-10-05 ｜ 基线：后端 373 测试通过 / 提交 `ca8c02a`

---

## 1. 现状对齐：核心目的落地到什么程度

### 1.1 硬约束（实测数据，决定了所有方案的边界）

| 项 | 实测值 | 含义 |
|---|---|---|
| 显存 | **15741 / 16311 MiB** | **余量仅 570 MiB** |
| `max_loras` | **2** | GPU 上最多同时常驻 2 个 LoRA |
| `max_cpu_loras` | 4 | 其余在 CPU 侧，换入需要传输 |
| 当前常驻 | `extract_v2` + `paper_analyzer_v6` | 正好占满 2 个 |
| 适配器权重 | r8 = 63 MB / r16 = 126 MB | 多常驻一个 r16 约需 +126 MB |

### 1.2 LoRA 清单（10 个，但只有 6 个能用）

| 类别 | 适配器 | 说明 |
|---|---|---|
| ✅ 当前底座可用（Qwen3-4B-Instruct） | `extract_v1`(r8) `extract_v2`(r16) `paper_analyzer_v5`(r8) `paper_analyzer_v6`(r16) `test_agent_v1`(r16) `testlora`(r8) | 6 个，共 567 MB |
| ❌ **底座不匹配** | `frontend-ui-architect-lora`(qwen2.5-coder-14b) `json_extract`(Qwen2.5-7B) | 当前 vLLM **加载不了** |
| ❌ **文件不完整** | `ml_engineer` `strict_json` | 缺 `adapter_config.json` |

**这直接说明一个缺口**：配置里可以引用任意 LoRA 名，而**没有任何预检**。用户引用一个底座不匹配或损坏的适配器，
要等到该节点执行时才失败（或更糟：LoRA 被忽略而用底座出结果）。

### 1.3 当前工作流的真实形态

```
input → [extract_method / extract_dimensions] → [analyze_method / analyze_data /
        extract_claims / critique_analysis] → finaloutcome          （kb_context 并行供检索）
```

5 种节点类型：`input` `retrieval` `process` `terminal` `aggregate`。
**这五种全是"管道类型"——描述数据怎么流，不描述"干什么活"。**
"提取方法""批判性分析"这些**任务语义只存在于 prompt 文本里**，机器不可见、不可校验、不可复用。

## 2. 五个缺口（都有代码级证据）

| # | 缺口 | 证据 |
|---|---|---|
| G1 | **节点功能不明确**：类型是管道语义，任务语义藏在 prompt | 5 种类型无一是任务类型；`paper_analyzer_v5` 做"七维度抽取"、`v6` 做"方法深度分析"，区别只在 prompt |
| G2 | **未知节点类型静默降级** | `workflow_engine.py`: `ntype = node.get("type", "process")`，随后只判 `input`/`retrieval`，**其余一律走 process 路径** |
| G3 | **字段无单一真源** | 节点字段已 16 个（本会话新增 11 个），而 `normalize_config()` 只声明 `position/provider/model_override` 三个默认值；引擎靠 `.get(..., 默认值)` 内联读取 → **字段名拼错会被静默忽略** |
| G4 | **Agent 路径与 UI 能力不对齐** | `AGENT_TOOLS.add_workflow_node` 只写 9 个字段（`id/type/description/input_from/lora/prompt/position/provider/model_override`），**缺 `output_format`/`chunk_size`/`chunk_workers`/`cache`/`temperature` 等 11 个**；且 `input_from` 恒为 `[]`（无法建依赖）→ **本会话做的分块抽取配方，Agent 根本配不出来** |
| G5 | **兼容检查只覆盖 LoRA 存在性** | `check_config_compat()` 只比对 `scan_loras()` 的名字，且**仅在 `/workflow/config/import` 时调用**；不查底座匹配、provider 配置、KB 是否存在、节点类型、字段合法性 |

> 本会话已两次踩到 G3/G4 类问题：Agent 路径漏字段；C1 加多配置后 Agent 仍写默认配置
> （已修：5 处 Agent 配置读写现在跟随所选配置）。

## 3. 优化方向与可行性判断

可行性判据：**是否受硬件/外部约束**、**是否需要动核心循环**、**能否单测覆盖**。

### 第一组：节点模型（对应"节点功能明确"）

| # | 方向 | 做法 | 可行性 | 成本 | 风险 |
|---|---|---|---|---|---|
| **D1** | **节点类型注册表（单一真源）** | 声明 `{类型, 字段清单, 默认值, 输出契约, 需要的 LoRA 角色}`；引擎、前端编辑器、Agent 工具、配置校验**全部读它** | **高**（纯重构，无外部依赖） | 中 | 低（373 测试 + 配置自检兜底） |
| **D2** | **语义任务节点** | 在 D1 之上定义任务型节点：`extract_method` / `analyze_method` / `translate` / `critique`…，每个绑定 `{LoRA 角色, 指令模板, 输出 schema, 输入槽}` | **高** | 中 | 低 |
| **D3** | 输出契约校验 | 每类型声明 `output_schema`（必填字段/类型），不满足 → 降级（路线图 A1） | **高** | 低 | 低 |
| **D4** | **未知类型不再静默** | 未知 `type` → 明确报错，或按 process 处理但记入 `degraded` 并在日志/报告标明 | **高** | **极低**（几行） | 极低 |

> D2 是"让节点功能明确"的真正落点：类型即任务、字段即契约、LoRA 角色即依赖。
> 例如 `extract_method` 节点应自带"指令模板 + output_format=text + 分块 + cache + 需要的 LoRA 角色=extractor"，
> 用户只需连线，不必手填 8 个字段。

### 第二组：LoRA 编排（对应"高精度低显存"这一核心目的）

| # | 方向 | 做法 | 可行性 | 成本 | 风险 |
|---|---|---|---|---|---|
| **L1** | **LoRA 预检（跑前）** | 检查每个节点的 LoRA 是否已安装、**底座是否匹配**（`check_lora_compatibility` 已有）、provider 是否配好、KB 是否存在；不通过就**拒绝启动** | **高** | 低 | 低 |
| **L2** | **LoRA 感知调度（减少换入换出）** | 在**不破坏依赖**的前提下，把同 LoRA 的节点排在一起（同层内按 LoRA 分组） | **高**（纯排序，可单测：断言 swap 次数下降） | 低-中 | 低 |
| **L3** | 换入换出可见化 | 记录每次 `load` 的次数与耗时 → `_meta.lora_swaps` | **高** | **极低** | 极低 |
| **L4** | 提高常驻数（2 → 3/4） | 需重新平衡显存 | **中低**：余量仅 570 MiB，+2 个 r16 ≈ +252 MB，理论可行但几乎不留余量 | 中 | **中高**（OOM 风险）→ 必须实测，且建议先降 `max_model_len` 或 `max_num_seqs` |
| **L5** | 单请求内多 LoRA 批处理 | vLLM 支持批内多 LoRA | 中（我们是逐节点串行，收益有限） | 中 | 低 |
| **L6** | 路由并发安全 | `router.ensure` 加锁 + 仅同 LoRA 波次并行 | **高** | 低 | 低（也是 A4 的前置） |
| **L7** | **一适配器服务多任务**（最省显存） | `extract_v2` 已用**同一个适配器**覆盖 5 个抽取任务（方法/数据/问题/贡献/结论） | **高**（已在做） | — | — |

> **L7 是最重要的结论**：在 `max_loras=2` + 余量 570 MiB 的约束下，
> "**一个适配器覆盖一族任务**"比"多适配器轮换"更符合"高精度低显存"。
> 应把它写成模板设计原则；反面教材是 `paper_analyzer_v5`（七维度）与 `v6`（方法分析）
> 两个适配器做同一篇论文的一件事——既有换入换出成本，又都没有被评测过。

### 第三组：模板体系（对应"支持开发多种模板"）

| # | 方向 | 做法 | 可行性 | 成本 | 风险 |
|---|---|---|---|---|---|
| **T1** | **模板 manifest** | 每个模板声明 `{需要的 LoRA/底座/provider/KB, 说明, 参数}`；与 L1 预检共用 | **高** | 低 | 低 |
| **T2** | 模板画廊 | 下拉升级为卡片列表（名称/用途/节点数/需求是否满足/一键切换+克隆） | **高**（C1 已有多配置后端） | 中（前端） | 低 |
| T3 | 模板参数化 | 模板内留变量（语言、top_k、输出格式），运行时填；`render_prompt` 已具备替换能力 | 中 | 中 | 中（需与节点字段区分） |
| T4 | 模板版本与迁移 | 已有 `schema_version`；加 `min_engine_version` + 迁移函数 | 中 | 中 | 中 |
| **T5** | 模板打包/导入导出 | import/export 已有 ✓，只差打包规范（zip：config + 说明 + 样例） | **高** | 低 | 低 |

### 第四组：自定义节点兼容性（对应"添加后兼容需要齐全"）

| # | 方向 | 做法 | 可行性 | 成本 | 风险 |
|---|---|---|---|---|---|
| **X1** | **字段 + 类型 linter** | 未知字段/未知类型/非法取值 → 明确报错（现在静默忽略） | **高** | 低 | 低 |
| **X2** | 前端编辑器按注册表渲染 | 消除 `if/else` 硬编码，新字段自动出现在所有相关节点 | **高** | 中（前端重构） | 中（回归面大，有前端测试兜底） |
| **X3** | **Agent 工具与 UI 能力对齐** | `add/update` 支持全部字段；**并从 prompt 的 `{节点id}` 自动反推 `input_from`** | **高** | 低-中 | 低 |
| **X4** | 节点字段默认值集中声明 | `normalize_config` 扩为字段注册表驱动的补全，老配置自动补齐 | **高** | 低 | 低 |
| **X5** | **前后端字段一致性测试** | 由注册表生成字段清单快照；断言「前端可设字段集合 ⊇ 引擎读取字段集合」 | **高** | 低 | 低 |

> X5 是**防复发机制**：本会话已经两次因为"加了字段但某条路径漏了"出问题。
> 有了这个测试，以后加字段漏改 Agent 或前端会直接测试失败。

### 第五组：可观测与体验

| # | 方向 | 做法 | 可行性 | 成本 | 风险 |
|---|---|---|---|---|---|
| O1 | **dry-run** | 只校验 + 估算（LoRA 是否齐、token 预算、节点数、预计换入换出次数），不执行 | **高** | 中 | 低 |

## 4. 建议路线

### 阶段一：低成本高收益（可立即做，不改架构）

1. **D4** 未知类型显式化（几行）
2. **L1** LoRA 预检 —— **这一项直接对应"高精度"**：现在配置引用的 `paper_analyzer_v5/v6` 从未被评测过
3. **L3** 换入换出计数 + **L2** LoRA 感知调度（先有度量再优化）
4. **X1** 字段/类型 linter + **X4** 字段默认值集中
5. **X3** Agent 工具字段对齐 + `input_from` 自动反推
6. **L6** `router.ensure` 加锁（为 A4 铺路）
7. **X5** 前后端字段一致性测试（防复发）

### 阶段二：结构性改造（机制部分 ✅ 已完成，任务族待确认）

8. **D1 节点类型注册表** —— 单一真源，一次解决 G1/G3/G4
9. **D2 语义任务节点** —— 让"节点功能明确"落地
10. **X2** 前端编辑器按注册表渲染
11. **D3** 输出契约 + 校验

### 阶段三：模板与编排

12. **T1/T2/T5** 模板体系（manifest + 画廊 + 打包）
13. **O1** dry-run、**O2** 耗时面板、**O3** 可溯源率
14. **A4** 节点并发（单独一轮）

### 明确不建议现在做

| 项 | 原因 |
|---|---|
| L4 提高 `max_loras` 到 4 | 余量仅 570 MiB，OOM 风险高；应先降 KV / `max_num_seqs` 并实测 |
| L5 单请求多 LoRA | 逐节点串行下收益有限 |
| 为每个 prompt 新建一个节点类型 | 类型应是**任务族**（抽取/分析/校验/汇总），否则类型爆炸、维护不动 |
| 盲目扩 LoRA 数量 | 与"低显存"目标冲突；应先做 L7（一适配器多任务）与 L2（减少 swap） |

## 5. 一句话结论

**当前工作流的骨架是好的**（依赖图、失败显形、分块、缓存、多配置都已具备），
但它现在是**"管道 + prompt 约定"**，而不是**"任务节点 + 契约"**。
要让它成为"动态多 LoRA 任务平台"，关键动作只有三个：

1. **D1 注册表**：把节点类型、字段、契约、LoRA 角色收进单一真源（解决 G1/G3/G4）
2. **L1+L2+L3**：跑前预检 + 减少换入换出 + 度量（把"低显存"从口号变成指标）
3. **T1**：模板带 manifest，让"多模板"成为可校验、可分享的资产

而**最符合其核心目的的设计原则**是 **L7：一个适配器覆盖一族任务**。
在 `max_loras=2`、余量 570 MiB 的约束下，这条路比"堆适配器"更能同时满足高精度与低显存。

# 附录：语义任务族草案（阶段二，**待你确认**）

阶段二已落地的机制：**类型即契约** —— `NODE_TYPE_SPECS` 声明每个类型的
`{中文标签, 输出形态(text/json), 默认字段, LoRA 角色, 用途}`，
引擎按类型自动补齐默认字段，前端与 Agent 从同一份清单驱动（有 X5 一致性测试守着）。

## A. 已实现（你现有配置里本来就在做的事，只是现在有了名字）

| 类型 | 标签 | 用途 | 输出 | LoRA 角色 |
|---|---|---|---|---|
| `extract` | 🧩 抽取 | 从原文**逐字**抽取（可溯源）；长文自动分块并发并缓存 | text | extractor |
| `analyze` | 🔬 分析 | 对上游抽取结果做结构化分析 | json | analyzer |

实测：新建 `extract` 节点只需写 `type + prompt + lora`，
即自动获得 `chunk_size=3000 / overlap=500 / workers=4 / cache=true / temperature=0`，
输出与手工调好的配方一致（1455 字），第二次运行 **0 秒命中缓存**。

## B. 建议补充的任务族（请你裁剪）

| 类型 | 用途 | 输出 | LoRA 角色 | 对应既有问题 |
|---|---|---|---|---|
| `verify` | 把报告里的数字/缩写回查抽取结果，给出**可溯源率** | json | 无（纯规则即可） | 路线图 A2 |
| `translate` | 把英文抽取结果翻成中文（或反之） | text | translator | 抽取式 LoRA 输出原文语言，报告要中文 |
| `critique` | 批判性分析：过度声明、未验证假设 | json | critic | 你配置里已有 `critique_analysis` 节点 |
| `compare` | 对比两篇论文 / 两次运行 / 两个 LoRA 输出 | json | 无 | 评测闭环的延伸 |

**不建议新增**：`summarize`（已被 `aggregate` 覆盖）、`review`/`grade`（属评测脚本职责，不进工作流）。

## C. 需要你定的三件事

1. **任务族清单**：B 表里的 `verify` / `translate` / `critique` / `compare` 要哪些？还有缺的吗？
2. **LoRA 绑定方式**（影响"开箱可用"程度）：
   - **方案 a（灵活）**：类型只声明**角色**（如 extractor），节点里再选用哪个 LoRA —— 换 LoRA 不用改类型
   - **方案 b（省事）**：类型直接绑定具体 LoRA（如 `extract` → `extract_v2`）—— 用户只连线
   - 可折中：类型给**推荐 LoRA**，节点未指定时自动采用
3. **是否自动迁移**现有配置里的 `process + output_format=text + chunk_*` 节点为 `extract`？
   （迁移更整齐，但会改动你现有配置文本）
