## 二、V6.1 计划（**优先级排序**）

### 🥇 步骤 1：扫描信号提炼（**价值最高** ✓）

**问题**: `scan` 只记"缺什么" ✗ 没提炼成**可写的工具规格** ✗
**做法**:
```
① 从轨迹里找"失败但有意图"的片段 ✓
   例: Agent 反复调 list_upload 但用户要的是"读上传文件" ⇒ 可能是缺 read_upload_by_name ✓
② 用 LLM 把「缺什么 + 上下文」**提炼成工具规格**:
   {name, desc, params, returns, examples}
③ 存成 draft 候选 ✓ 交给 check 闸门 ✓
```
**工时**: 3h · **依赖**: 无 GPU ⚠ 但需 LLM（vLLM 3060 ✓）
**验收**: 从 16 条 signals 里提炼出 ≥3 个**结构合理**的规格 ✓

### 🥈 步骤 2：注册后自动 A/B（**最可靠的质量保证** ✓）

**问题**: 注册完不知道好不好用 ✗
**做法**:
```
① approve 注册后 ⇒ 自动跑一个小 A/B:
   · 用 5 个相关任务跑"有/无该工具"两臂 ✓
   · 比较工具调用成功率 + 任务完成率 ✓
② 结果写进 _tool_docs.json 的 usage_stats ✓
③ 若 A/B 变差 ⇒ 自动**警告**（不自动回滚 ✗ 要人确认 ✓）
```
**工时**: 3h · **依赖**: GPU（跑批 ⚠ 会占 3060 ✓）
**验收**: approve 后能自动产出 A/B 报告 ✓

### 🥉 步骤 3：撤销机制（**安全必需** ✓）

**问题**: 注册错了只能手动恢复备份 ✗
**做法**:
```
· `tool_forge.py undo <name>` ⇒ 从最近的 .bak_ts 恢复该工具 ✓
· `tool_forge.py history` ⇒ 列出所有注册/撤销记录 ✓
· 保留审计日志 ✓
```
**工时**: 1.5h · **依赖**: 无 GPU ✓ **零风险** ✓
**验收**: 注册→撤销→工具消失 ✓ 且 _tool_docs.json 与撤销前一致 ✓

### 步骤 4：工具组合生成（**最有想象力但最难** ⚠）

**问题**: 只会单工具 ✗ 不会"串成更高层工具" ✗
**做法**:
```
① 从轨迹里找**重复使用的工具序列** ✓
   例: [list_knowledge_bases → query_knowledge_base → read_docx] 反复出现 ✓
② 提议把它封装成 `query_kb_and_read` 一个工具 ✓
③ 生成组合器代码（调用已有工具 ✓ 不新写逻辑 ✓）
```
**工时**: 4h · **风险**: 组合器可能**放大错误** ✗
**验收**: 提议 ≥1 个组合器 + 人工判断合理性 ✓

### 步骤 5：UI 审核页（**体验必需但可后做** ✓）

**问题**: 全靠命令行 ✗
**做法**:
```
· 前端加「工具锻造」页 ✓
· 列出 draft 候选 ✓ 显示 4 闸检查结果 ✓
· 一键 approve / reject ✓
```
**工时**: 4h · **依赖**: 无 GPU ✓
**验收**: 能在界面完成 draft→check→approve 全流程 ✓

### 步骤 6：工具质量评分（**长期** ⚠）

```
· 每个工具记 usage_count + success_rate + avg_latency ✓
· 低分工具标"待改进" ✓
· 从未用的工具标"待删" ✓
```
**工时**: 2h · **依赖**: 需累计使用数据 ⚠
