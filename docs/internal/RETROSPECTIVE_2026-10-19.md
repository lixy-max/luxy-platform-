```
✅ 正确顺序：
   提出需求 → 【查文献/开源】→ 有现成方案？→ 用现成的 ✓
                          → 没有？→ 小规模验证 → 大规模投入

❌ 我们做的：
   提出需求（LoRA 训练平台）→ 直接动手 ✗ → 三轮试错 ✗ → 才想起来查文献 ✗

```
如果没查文献 ⇒ 会继续做：

  ⇒ 总计 63h 会投在【错误的前提】上 ✗✗

# 第三部分 · ★ 两条项目原则（教训固化 · 写进项目）

> 用户要求：「我希望这个深刻教训可以作为我们项目的两点」

## 原则一：**调研先行**（Research First）

```
任何"要不要做 / 怎么做 / 期望多少收益"的决定，
必须【先查文献 + 查开源】再动手 ✓

具体规则：
  ① 新方向开工前，必须先有【文献依据】（≥2 篇 ✓）
  ② 没有文献依据的方向 ⇒ 最多做【2 小时小验证】✗ 不许大规模投入 ✗
  ③ 文献结论要进 `docs/LITERATURE_REGISTRY.md` ✓（本次已建 ✓ 见附件）
  ④ 决策要写清「依据哪篇文献的哪条结论」✓
```

**这次的证据**：查文献 2h 救回 63h 错误投入 ✓

---

## 原则二：**先找不训**（Search Before Train）

```
当用户想要一个"什么样的模型"时，
不是直接闷头训练 ✗ 而是【优先去找现成的】✓

查找优先级（从高到低 ✓）：
  ① 现成的模型（HF/ModelScope 上有没有已发布的？）✓
  ② 现成的 LoRA（社区有没有训好的同能力 LoRA？）✓
  ③ 现成的 API/服务（云服务能不能直接覆盖？）✓
  ④ 提示词/检索方案（能不能不改模型解决？）✓ ← A7/A8 证明这个能 +36~56% ✓
  ⑤ 最后才考虑自己训练 ✓
```

**为什么这条对我们特别成立** ✓：
```
我们平台有【浏览器自动化】✓（web_* 工具 + drill 浏览器 ✓）
⇒ 可以自动去 HF / ModelScope / GitHub / 论文库检索 ✓
⇒ 把"找"这件事做成平台能力 ✓（不是人工查 ✗）
⇒ 这正是我们平台的【差异化价值】之一 ✓✓
```

**这次的反例**：
```
我们想要"工具调用更强" ⇒ 直接自己训 LoRA ✗（三轮 ✗）
正确做法 ⇒ 先找：NexusRaven 7B ✓ Hammer-7B ✓ xLAM-7B ✓ 都是开源的 ✓
         ⇒ 直接下载/对比/选一个 ✓ 比训练快 100 倍 ✓
```

## 原则三（衍生）：**评测口径必须先行**

```
训练之前先定义"怎么算成功"✓ 否则训完也不知道好坏 ✗
  · 指标要具体（工具选择准确率 ✓ 不是总分 ✗）
  · 样本量 ≥30 ✓
  · 必须有 base 对照臂 ✓
  · 环境要隔离（快照/还原 ✓ 防漂移）
```
