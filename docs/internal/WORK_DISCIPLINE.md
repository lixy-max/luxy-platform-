## 零、绝不凭印象写「事实性常量」（2026-10-21 补 · 血泪教训）

**规则：版本号 / API 参数名 / 字段名 / 端口 / 路径 / 概率语义 —— 一律先查证再落盘。**

### 真实事故

```json
// 我凭印象写的 package.json
"playwright-core": "^25.0.0"
```

- playwright 真实版本是 **1.4x–1.6x**，`25.0.0` **根本不存在**
- `npm install` → `npm error notarget No matching version found`
- ⇒ 依赖装不上 ⇒ sidecar 起不来 ⇒ 浏览器自动化 100% 失败
- 而我以为"是网络/镜像问题"，于是在错误前提上又修了 5 个次要 bug
- **一条 `npm view playwright-core version` 就能避免整天的返工**

### 必须查证的清单

| 类型 | 查证方式 |
|---|---|
| npm 包版本 | `npm view <pkg> version` / `npm view <pkg> versions` |
| PyPI 包版本 | `pip index versions <pkg>` |
| API 参数名 | 读真实调用方代码 / 抓真实请求体（不靠记忆）|
| 字段语义（如 prob） | 读实现 + 用已知样本验证方向 |
| 端口 / 路径 / IP | `ss -lntp` / `ip route` / 实际测试连通性 |
| 外部服务地址 | 从配置或环境变量读，不硬编码猜测 |

### 连带教训：先抓证据，再下结论

- ❌ 「上下文 32768」被我误读成「上一文 32768」→ 错判 3 次
- ✅ 正确做法：**抓真实请求体**（`page.on('request')`）→ 一眼看到 system 里塞了假论文

**结论：任何"看起来像常量"的东西，都是可以用一条命令查到的。查一次，省一天。**

## 一、开长任务前：必须挂监视器

**规则：凡是 > 5 分钟的作业，一条命令启动 + 一个后台监视器，不许"等一下再看"。**

| 场景 | 必须做 |
|---|---|
| 训练 / 评测 / 渲染 / 批量下载 | 启动时**同时**起后台轮询 job（`run_in_background: true`） |
| 需要多次查看进度 | 写 `monitor_*.sh`，轮询日志关键字（`ALL DONE` / `完成` / `Traceback`）|
| 服务重启 | 循环 `curl /health` 直到 200，超时报错，**不许 sleep 固定秒数就假设成功** |

**反面例子（真实踩过）**
- 训练 15 分钟没盯 → 中途 vLLM 被停 → 白跑
- 评测 30 分钟没盯 → DSH 重启把子进程带走 → 数据全丢
- 后端重启后 `sleep 25` 就假设好了 → 实际旧进程没死，新进程绑不上端口 ✗

**正确模板**
```powershell
# 启动（脱离子进程）
$r = Invoke-CimMethod -ClassName Win32_Process -MethodName Create -Arguments @{CommandLine=$cmd}
# 监视（后台 job，完成会通知我）
for ($i=0; $i -lt 80; $i++) { Start-Sleep 15; if (日志含 ALL DONE) { break } }
```

## 二、动手写代码前：必须查资料

**规则：凡是"我不知道最佳实践"的实现，先查再写。**

| 领域 | 必查 |
|---|---|
| 视频 / 动画 / Remotion | 官方文档 + 开源项目实现（镜头语言、缓动、转场）|
| 前端 UI / 配色 | 设计系统规范（不要凭感觉配色）|
| 训练 / 评测 / 统计 | 论文 + 协议（样本量、显著性、校准）|
| 第三方库 bug | 错误信息原文 + issue 搜索 |

**反面例子（真实踩过）**
- 视频转场只会 `translate` + `scale` → 用户说"太单一" ✗
- `playwright-core@^25.0.0` 不存在 → 查都不查就写进 package.json ✗
- `confidence` 概率语义（成功 vs 失败）靠猜 → 反了整整两轮 ✗

**查完要落成一句可执行结论**，例如：
> "Remotion 里所有动画必须 `useCurrentFrame()` 驱动；spring damping=200 为平滑。"

## 三、测量前：必须验样本有效性

**规则：任何"XX 坏了"的结论，先证明测量本身没问题。**

必查三项：
1. **输入是否齐全**（调工具要传 `tools` schema ✗ 不传当然 0 次调用）
2. **样本量够不够**（n<15 不对显著性下结论）
3. **数据是新还是旧**（旧快照 ≠ 当前状态）

**反面例子（真实踩过 4 次）**
- 没传 tools schema → 报"92 工具一次不调" ✗
- 用旧轨迹算工具质量 → 报"14 个 D 级" ✗（实际 0 个）
- n=15 下"不显著"结论 → n=30 后 p=0.028 显著 ✓
- 置信度 prob 语义猜反 → 全盘结论反 ✗
